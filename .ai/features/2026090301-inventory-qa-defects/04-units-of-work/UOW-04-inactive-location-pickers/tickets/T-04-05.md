# T-04-05 — Chỗ rò thứ hai của auto-fill

## Context

`StockTakeFormDialog.tsx:454-470`:

```ts
const params = new URLSearchParams({ page: "1", pageSize: "1", itemId, storageId: effectiveStorageId });
const { data } = await apiClient.get<PaginatedResponse<BalanceRow>>(`/inventory/stock/balances?${params}`);
return data.data[0] ?? null;
```

`pageSize: 1` cộng thứ tự mặc định `loc.code ASC` (`stock-ledger.service.ts:578-593`) nghĩa là nó
lấy **kệ có mã đứng đầu bảng chữ cái**, đang theo dõi hay không. Kết quả nuôi `resolveItemDefaults`
(`:519+`) để đặt `locationId` / `locationCode`.

Đây là cùng một họ lỗi với In tem mã nhưng ở màn khác, và QA chưa gõ tới. Picker "Vị trí" của chính
màn này đã đúng (`:432-452` có `activeOnly`) — chỉ đường auto-fill là hở.

## Implementation summary

`fetchFirstBalance` now passes `isTracked=true` + `locationIsActive=true` (exact casing confirmed
against `BalanceQueryDto` in `stock-ledger.controller.ts:114,130`). With those two params the
single-row `pageSize: 1` result can only ever be a shelf that is both tracked-for-this-item and
active — satisfies AC-21's primary case.

**"No valid shelf remains" is more subtle than "filtered result is null"** — that case was split in
two, because `resolveItemDefaults`'s existing fallback (`fetchFirstLocation`, item-agnostic "first
active location of the storage") does **not** know about the item, so if left as the unconditional
fallback it could silently re-select the very shelf we just filtered out (an active location where
*this item* happens to be `is_tracked = false`) — reintroducing the exact bug under a different code
path. Added `hasAnyBalanceAtStorage(itemId)` (unfiltered, reads only `PaginatedResponse.total`) to
tell the two cases apart:
- item never had a balance row here at all → safe to keep the old "first active location" fallback
  (this is the legitimate "assigned but never received" default, not the bug).
- item has balance row(s) here but none passed the filter (all stopped/inactive) → `locationId`
  stays `""`.

For the *local-only* (new stock-take) row that's a genuinely empty cell the user can then fill in
via the "Vị trí" column picker (`:432-452`, unmodified, already `activeOnly`) — verified
`handlePickLocation`'s `else` branch resolves a bare local row by `location.id` with no dependency
on the row already having an id.

For the *persisted* (already-saved DRAFT stock-take) `handlePickItem` path, an empty `locationId`
can't just be left blank client-side — it has to `POST /inventory/stock-takes/:id/lines`, and that
endpoint's own `resolveLineLocation` → `findItemBalanceInScope`
(`apps/api/.../stock-take/stock-take.service.ts:1532-1550`) falls back to
`ORDER BY sb.quantity DESC` with **no `is_tracked` / `loc.is_active` filter at all** when
`locationId` is omitted. Sending `undefined` there would silently delegate to a differently-broken
resolver — worse, it directly violates A-13 (`quantity` is not a valid substitute for `is_tracked`).
Since that file is not in this ticket's `touches`, the chosen fix is to refuse client-side: if
`resolveItemDefaults` returns no `locationId`, `handlePickItem`'s edit-mode branch shows a toast
("... chọn vị trí thủ công") and does not call the API, instead of ever sending a request that could
come back with a stopped shelf.

**Finding — flag for a follow-up ticket:** `stock-take.service.ts`'s `findItemBalanceInScope`
(used by both `addLine()` and `create()` for lines saved without an explicit `locationId`) has the
same class of bug as the one this UOW is fixing everywhere else in the frontend — it is backend code
and out of this ticket's `touches`, so it was not changed, but AC-21's guarantee is currently only
airtight in the client. A saved stock-take line created through `create()` (the batch endpoint used
when the whole take is first saved) with no explicit `locationId` per line would still be exposed to
this same resolver.

**Sort-criterion note (required by the ticket):** kept `loc.code ASC` + `pageSize: 1` exactly as
instructed — not changed. My read: quantity-based selection would arguably be a *more useful*
default for kiểm kê (bias toward the shelf most likely to actually hold stock), but that's a
genuine UX call for whoever owns this screen, not something to decide unilaterally inside a bugfix
ticket — flagging per the ticket's own instruction rather than acting on it.
