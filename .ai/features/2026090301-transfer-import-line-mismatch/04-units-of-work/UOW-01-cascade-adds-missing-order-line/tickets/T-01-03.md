# T-01-03 — E2E: sửa phiếu xuất rồi nhập, chạm Postgres thật

## Context

Đây là ticket quan trọng nhất của UoW, vì nó là thứ đã thiếu lần trước.

Commit `609b2922` có kèm unit test viết riêng để chặn đúng bug này
(`transfer-order.service.spec.ts:1085`, *"inserts a transfer_order_lines row for an item
the order never carried"*). Test đó **xanh** suốt 10 ngày trong khi bug sống nguyên trong
prod, vì nó mock:

```ts
dataSourceManagerQuery.mockResolvedValueOnce([]);   // length 0 → nhánh insert chạy trong test
```

Còn TypeORM thật trả `[[], 0]` — length 2 → nhánh insert **không** chạy ngoài đời. Mock
đã mã hoá một hiểu lầm rồi bảo kê cho nó. Nên ADR-02: lớp lỗi này phải được chứng minh
trên Postgres thật.

## Implementation notes

- Dựng theo khuôn e2e sẵn có trong `apps/api/test/e2e/` (global-setup tự tạo và migrate
  `erp_test`; suite chạy `maxWorkers: 1`).
- Kịch bản, đi qua **đúng các API mà UI dùng**, không insert tay:
  1. Tạo lệnh điều chuyển từ chi nhánh gửi, có dòng A (3) và B (5); chuyển sang
     IN_PROGRESS để sinh phiếu xuất.
  2. `PATCH /inventory/goods-issues/:id` sửa phiếu xuất **một lần**: xoá B, đổi A thành 4,
     thêm C (2) — đúng bộ ba thao tác QA đã làm (A-02).
  3. Khẳng định **trên bảng**: `transfer_order_lines` của lệnh có A = 4, B = 0, và một
     dòng C = 2 với `source_location_id` không rỗng. Truy vấn thật, không đọc từ service.
  4. `POST /inventory/transfer-orders/:id/import` với actor ở chi nhánh nhận, lines soi
     gương theo phiếu xuất (đúng như FE `prefillFromTransferOrder` gửi).
  5. Khẳng định trả **201, không phải 400**; phiếu nhập có đúng hai dòng A và C.
- Không mock `dataSource.manager.query` ở bất kỳ đâu trong suite này — nếu mock, ticket
  này mất toàn bộ ý nghĩa.
- Cảnh giác bẫy đã biết: teardown của kafkajs treo làm suite thoát code 1 dù test đậu —
  đọc kết quả test thật, đừng tin exit code ([[reference_e2e_outbox_relay_race]]).

## Kết quả chạy

```
npx jest --config ./test/e2e/jest-e2e.config.ts transfer-order-export-edit-then-import
  → passed 2/2
```

**Phép thử quyết định.** Hoàn nguyên đúng một dòng của T-01-02
(`affectedRowCount(updated)` → `(updated as any).length`) rồi chạy lại:

```
WITH OLD CODE → passed 0/2  failed 2
  RED: carries all three edits of one save onto the order: A changed, B zeroed, C inserted (AC-05)
       Error: expect(received).toBeDefined()   Received: undefined
  RED: lets the destination receive what the edited issue actually carries — no 400 (AC-02)
       Error: expected 201 "Created", got 400 "Bad Request"
```

Dòng `expected 201 "Created", got 400 "Bad Request"` **chính là QA #8**, lần đầu tiên
được tái hiện trong một test tự động thay vì trên màn hình người dùng. Khôi phục bản sửa
→ 2/2 xanh trở lại.

Đây là bài kiểm tra mà bản sửa 24/08 chưa bao giờ có: unit test đi kèm nó **không** đỏ
khi bug quay lại, nên nó chưa từng là test hồi quy.

## Đọc kết quả suite cho đúng

Jest báo `success: false` kèm:

```
● Test suite failed to run
  QueryFailedError: relation "outbox_messages" does not exist
      at OutboxRelayService.pollOnce (src/modules/events/outbox/outbox-relay.service.ts:70)
```

Đây **không phải** test đỏ: cả 2 test đều `passed`. Đó là bẫy đã biết —
`OutboxRelayService` poll nền đua với `resetDatabase()`, làm suite thoát mã khác 0
([[reference_e2e_outbox_relay_race]]). Đọc `numFailedTests`, đừng đọc exit code. Bẫy này
có sẵn với mọi suite e2e gọi `resetDatabase()`, không phải do ticket này gây ra.

## Ghi chú dựng fixture

Hai chi nhánh thật, hai lần đăng nhập — **không** dùng một token rồi đổi header
`X-Branch-Id`: `ActorContext` lấy `branchId` từ JWT trước header, nên đổi header không
đưa actor sang chi nhánh khác. Lấy khuôn từ `goods-receipt-from-transfer.e2e-spec.ts`.

Ba mặt hàng phủ đúng ba thao tác QA làm trong **một** lần lưu: A đổi số lượng 3→4,
B xoá hẳn, C thêm mới (A-02).
