# T-01-01 — DTO + CTE theo itemIds

## Context
`pos-catalog-sql.ts` đã có `buildExactMatchCte` và `buildSuggestCte` từ
[[project_pos_catalog_search_perf]]; đây là nhánh thứ ba, đơn giản nhất — lọc thẳng
theo khoá chính.

## Implementation notes
- `buildItemIdsCte({ org, itemIds })` trả:
  ```sql
  SELECT i.id
    FROM items i
   WHERE i.organization_id = $1
     AND i.id = ANY($3::uuid[])
     AND i.is_active = true
     AND i.is_pos_visible = true
  ```
  **`= ANY($n::uuid[])`, không nội suy id vào chuỗi SQL.** Hai builder kia chỉ nhận
  placeholder nên chưa từng chạm dữ liệu người dùng; cái này nhận một mảng, và nội
  suy nó là cách duy nhất để mở lỗ SQL injection trong file này.
- Lọc `is_active`/`is_pos_visible` giữ nguyên: một item bị ngừng bán giữa phiên sẽ
  rơi khỏi kết quả, và caller xử được (dòng giỏ giữ `onHandUnknown` → cảnh báo bật).
- `PosCatalogStockQueryDto`: `itemIds: string[]` với `@IsArray`, `@ArrayNotEmpty`,
  `@ArrayMaxSize(200)`, `@IsUUID('4', { each: true })`, `@ApiProperty({ type: [String] })`.
- Comment tiếng Anh ([[feedback_no_vietnamese_in_backend_source]]).

`buildItemIdsCte` — spec khẳng định SQL sinh ra:
- chứa `= ANY($3::uuid[])`
- **không** chứa dấu nháy đơn nào, **không** chứa `IN (` → không có đường nội suy id

- chỉ nội suy đúng hai placeholder được truyền vào

`PosCatalogStockQueryDto` chạy qua **đúng** cấu hình `ValidationPipe` toàn cục
(`main.ts:33`):

| Input | Kết quả |
|---|---|
| 3 UUID hợp lệ | pass |
| `[]` | **reject** (ADR-02 — client phải bail, không hỏi rỗng) |
| thiếu `itemIds` | reject |
| có phần tử không phải UUID | reject |
| 201 phần tử | reject |
| đúng 200 phần tử | pass (trần là 200, không phải 199) |
| kèm field lạ | reject (`forbidNonWhitelisted`) |
