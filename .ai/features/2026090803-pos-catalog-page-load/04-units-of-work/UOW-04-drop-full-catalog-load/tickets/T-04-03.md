# T-04-03 — Bằng chứng payload + không hồi quy

## Context
AC-02 nói về **byte lúc mở trang**, và không unit test nào chứng minh được — phải đếm
trên network panel thật.

Bẫy đã có tiền lệ: API `:4000` có thể chạy từ checkout khác trỏ DB khác
([[reference_verify_stack_worktree_api_trap]]). Xác nhận `DB_NAME` trong
`apps/api/.env` và 0 dòng `EADDRINUSE` trong log của tiến trình mình bật, **trước** khi
kết luận.

Bẫy thứ hai, đã dính ở feature trước: phiên POS trong trình duyệt có thể là session
khôi phục của **org khác** với token mình tự mint. Kiểm `branchId` trong URL request
thật rồi mới đối chiếu số đo với DB.

## Implementation notes
- Viết `07-verification.md`: bảng request/byte trước–sau, kèm ảnh network panel.
- Đo cả ba chi nhánh nếu đăng nhập được: Cà Mau (10 400 item), Nha Trang (8 187),
  Hồ Chí Minh (1 730) — chi nhánh nhỏ là ca nơi thay đổi này ít lãi nhất, và cũng nên
  ghi lại.
- Chuyển kho nhanh: mở màn, tìm hàng, chọn kho nguồn, chụp màn hình (AC-11).
- `npx vitest run` từ `apps/pos-web`, không qua rtk.

| Payload catalog lúc mở trang (Hồ Chí Minh, 1 730 item) | 686 411 B | **8 638 B** |
| Payload catalog lúc mở trang (Cà Mau, 10 400 item) | ~3 844 kB | **8 638 B** |

Payload mới **không phụ thuộc kích thước chi nhánh** (`pageSize=30` cố định), nên chi
nhánh càng lớn càng lãi: Cà Mau tiết kiệm ~99,8 %.

Đã xác nhận API nói chuyện với `erp_dev_3008` và phiên trình duyệt thuộc org
`e60e5f49…` chi nhánh Cà Mau (kiểm `branchId` trong URL request, không suy đoán).

**Phát hiện lúc dọn dẹp:** `lsof -ti:4000` trả **hai** PID lạ (4463, 21634) ngoài
tiến trình tôi bật (63045) — có instance API cũ còn sống từ trước phiên này. Không
gây sai lệch ở đây (hai endpoint `/catalog/stock` và `/catalog/search` chỉ tồn tại
trong code của tôi, và chúng trả 201/200), nhưng đúng là hình dạng của bẫy
[[reference_verify_stack_worktree_api_trap]]. Đã kill cả ba khi test API-down và bật
lại một tiến trình sạch.
