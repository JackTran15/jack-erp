# T-04-03 — E2E xuất từng phiếu

## Context

Hai thứ chỉ e2e mới bắt được: header `Content-Disposition` thật sự sinh ra (nó do sink đặt,
không do controller), và điều kiện 404 xảy ra **trước** khi phản hồi mở. Cái thứ hai quan
trọng hơn cái thứ nhất: nếu 404 xảy ra muộn thì client nhận một file .xlsx hỏng kèm mã 200,
và không ai biết cho tới khi mở file.

## Implementation notes

- Khẳng định phản hồi là nhị phân: `expect(res.headers['content-type'])` chứa
  `spreadsheetml`, và `res.body` là `Buffer` có độ dài > 0.
- Khẳng định `content-disposition` chứa một tên file **không rỗng và không phải**
  `chung-tu.xlsx`.
- Ca 404: id ngẫu nhiên hợp lệ dạng uuid, và id của một phiếu thuộc tổ chức khác. Với ca
  thứ hai, `cash_receipts.organization_id` không có FK nên chỉ cần một uuid tổ chức bịa —
  không phải tạo org thật (bẫy đã ghi từ 2026090701).
- Khẳng định thân phản hồi 404 là JSON lỗi, **không** phải nhị phân — đó chính là bằng
  chứng phản hồi chưa từng bị mở dưới dạng file.
- Ca quyền (A-08): một tài khoản có `accounting.cash_receipt.read` xuất được phiếu thu tiền
  mặt; không cần dựng vai trò mới cho ca này.
- Suite chạy `maxWorkers: 1`, `forceExit: true`; đọc kết quả test, không đọc mã thoát.

## Found a real production bug (STOP, did not fix — out of `touches:` scope)

`VoucherXlsxWriter.writeTotalsRow` (`apps/api/src/modules/reporting/report-core/export/voucher-xlsx.writer.ts:322-343`)
calls `writeGridRow(...)`, which already calls `row.commit()` as its last line. `writeTotalsRow`
then calls `sheet.mergeCells(row.number, 1, row.number, span)` **after** that commit whenever
`labelSpan(this.grid) > 1`. In ExcelJS's streaming `WorkbookWriter`, a committed row is dropped
from memory, so this second merge throws `Error: Out of bounds: this row has been committed`.

All four treasury mappers (`cash-receipt-print.mapper.ts`, `cash-payment-print.mapper.ts`,
`bank-receipt-print.mapper.ts`, `bank-payment-print.mapper.ts`) share the same 3-column
`LINE_COLUMNS` shape — `description` (STRING), `categoryName` (STRING), `amount` (CURRENCY) —
which makes `labelSpan` return 2 for every one of them. So every `GET :id/export` call that
reaches `end()` with a non-null `totals` (i.e. every voucher with at least one line — the normal
case) crashes here. `voucher-xlsx.writer.spec.ts`'s fixtures never exercise this: their leading
column is always a NUMBER type (`stt`), which makes `labelSpan` return 1 and skips the buggy
branch entirely — so this was latent until ADR-05 made treasury vouchers the writer's first
consumer whose grid starts with two STRING columns.

Because `HttpResponseSink` sets headers in its constructor and `ExportPipeline` starts
streaming rows before this crash, the client has already received status 200 and the xlsx
headers by the time this throws — the request does not fail as a 500, it aborts mid-stream
(supertest reports `aborted`; a browser would show a broken/corrupt download). This is the
exact ADR-08 risk `HttpResponseSink`'s own doc comment names ("a failure can only end as a
broken download, never as a 4xx") — it fires on demand from `GET :id/export`, not only on a
row-fetch failure.

Fix belongs in `writeTotalsRow`: merge the label span inside `writeGridRow`'s per-slot loop
(same place the per-column `slot.span` merges already happen), before `row.commit()`, not as
a separate call on the row object after it returns. Left unfixed per this ticket's
`touches:` scope (test file only).
