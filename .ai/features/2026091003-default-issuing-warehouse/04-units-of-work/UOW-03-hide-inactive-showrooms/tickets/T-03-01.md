# T-03-01 — Tham số activeOnly cho GET /inventory/showrooms

## Context

`listShowrooms` (`inventory-location.service.ts:658-681`) lọc đúng ba thứ:
`organizationId`, `branchId`, `storageId`. Không có điều kiện active nào.

Không thể lọc thẳng trên `showrooms` vì `ShowroomEntity` (`showroom.entity.ts:9-25`) **không
có** cột active — trạng thái hoạt động của một showroom nằm ở kho backing nó, qua
`storage_id` → `storages.is_active` (A-08). Nên phải join.

Tham số là **tuỳ chọn, mặc định tắt** (ADR-03). `listShowrooms` có nhiều nơi gọi ngoài POS;
bật mặc định sẽ âm thầm giấu showroom ở những màn đó. AC-11 là test bảo vệ đúng điều này.

## Implementation notes

- Controller (`inventory-location.controller.ts:410-417`): ép kiểu `activeOnly` y hệt cách
  `listStorages` đang làm ở `:370-374` — chấp nhận `'true' | true | '1'`. Không tự nghĩ cách
  ép kiểu khác, hai endpoint cạnh nhau phải hành xử giống nhau.
- Service: chuyển từ `findAndCount({ where })` sang query builder để join được:
  ```ts
  const qb = this.showroomRepo.createQueryBuilder('sh')
    .where('sh.organization_id = :organizationId', { organizationId: actor.organizationId });
  // …branchId / storageId như cũ…
  if (activeOnly) {
    qb.innerJoin(StorageEntity, 'st', 'st.id = sh.storage_id AND st.is_active = true');
  }
  ```
  Dùng `innerJoin` (không `innerJoinAndSelect`) để hình dạng payload không đổi — thêm trường
  vào response là đổi hợp đồng ngoài phạm vi.
- `getManyAndCount()` để `total` khớp số dòng **sau** khi lọc. Đây là cái bẫy của việc chuyển
  từ `findAndCount`: nếu đếm trước khi join thì phân trang lệch.
- Giữ nguyên `skip` / `take` và nhánh sắp xếp `query.sortBy ? … : { createdAt: 'DESC' }`.
- Không đụng `getShowroomById`, `createShowroom`, `updateShowroom`.
