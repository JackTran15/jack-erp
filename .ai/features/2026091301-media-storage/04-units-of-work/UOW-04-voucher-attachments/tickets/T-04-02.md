# T-04-02 — Phiếu nhập kho — đồng bộ attachmentIds, trả attachments, đăng ký reader

## Context

Phiếu nhập kho đã nhận và lưu `attachmentIds` bất kỳ (`goods-receipt.service.ts:176,311-312`) và
detail trả nguyên entity (`:1095-1116`). Có **hai** đường tạo cùng khai `@Post()` trên
`goods-receipts`: legacy và v2 (`create-goods-receipt-v2.handler.ts:97`). `POSTED` vẫn sửa được
(`:267`), `CANCELLED`/`REVERSED` bị từ chối (`:251-257`) — đính kèm đi theo đúng luật đó (A-26).

## Implementation notes

- **Trước khi code**: chạy `SELECT count(*) FROM goods_receipts WHERE attachment_ids <> '[]'::jsonb`
  trên DB local (A-16), ghi kết quả vào Done when. Nếu > 0 thì dừng, `aidlc block` với lý do, và báo
  cần migration dọn.
- Tạo (legacy `:176`, v2 `:97`): sau khi có id phiếu, trong transaction sẵn có nếu có,
  `const ids = await mediaLink.syncOwner('GOODS_RECEIPT', id, dto.attachmentIds, actor, manager)` rồi
  ghi `attachmentIds = ids` (ADR-03).
- Sửa (`:311-312`): gọi `syncOwner` **sau** các kiểm tra trạng thái sẵn có (`:251-257`, `:267`); phiếu
  bị từ chối thì không bao giờ tới `syncOwner`.
- Detail (`:1095-1116`): thêm `attachments` từ `mediaQuery.listForOwners('GOODS_RECEIPT', [id], organizationId)`,
  chỉ `{ id, fileName, contentType, size }`.
- `onModuleInit`: `readerRegistry.register('GOODS_RECEIPT', (id, actor) => this.getById(id, actor).then(() => true, () => false))`
  — dùng đúng hàm đọc mà endpoint detail dùng, để phạm vi tải file bằng phạm vi xem phiếu.
