# T-01-02 — E2E: sku-breakdown row set with a stopped pair, a tracked empty pair and a no-balance pair

## Context

`getSkuBreakdown` has no test of its row set at all, and the unit spec T-01-01 adds only pins
the SQL text. The behaviour that matters — a stopped pair is not a row, in any period, and comes
back when re-tracked — needs the real `cells` CTE on Postgres. Write one new suite; do not extend
`inventory-stock-summary.e2e-spec.ts` (it is the v1 summary and keeping suites per UoW avoids
`uowg` touch hazards).

## Implementation notes

- Copy the shape of `apps/api/test/e2e/untracked-location-visibility.e2e-spec.ts:25-236`:
  `createTestApp` → `resetDatabase` → `seedBaseData`, `headers()` with `X-Branch-Id`, helpers
  `createLocation` (`POST /inventory/locations`, type `SHELF`), `createItem`
  (`POST /inventory/items`), `putBalance` (raw upsert into `stock_balances`, quantity 0) and
  `setTracking` (**the real** `PATCH /inventory/stock/balances/tracking`, so the stopped row is
  produced the way the UI produces it). Storage via `POST /inventory/storages` on `seed.branchId`
  (a non-main warehouse — the tracking endpoint refuses showroom pairs).
- Ledger history: insert `stock_ledger_entries` rows directly, as
  `inventory-report-v2.e2e-spec.ts:55-61` does (`reference_type = 'E2E_TEST'`, so
  `EXCLUDE_VOIDED_DOCS_SQL` never matches). Give the stopped pair one `+1` and one `-1` row inside
  a known month so its net is 0 (a stopped pair must sit at quantity 0 — `setBalanceTracking`
  refuses otherwise) but its `openingQty`/`inQty`/`outQty` would be non-zero if it leaked.
- Items: three standalone items (no `product_id`), so `groupKey` = the item id for each — the
  DTO's second `grp_items` arm. Call `POST /v2/inventory/stock/summary/sku-breakdown` with
  `{ groupKey, storageId, page: 1, limit: 50 }` (+ `startDate`/`endDate` for AC-02), expecting
  `200` (`@HttpCode(OK)` on the route).
- Fixture per AC:
  - **X** (AC-01/02/04): balance at `E01.01` qty 0 + ledger rows, then `setTracking(false)`;
    balance at `K09.01` qty 0, tracked. Assert rows' `locationId` set is `{K09.01}`, `total = 1`,
    `itemCount = 1`; with the month as period, assert `totals.openingQty/inQty/outQty` do not
    include the `E01.01` rows. Then `setTracking(true)` and assert `E01.01` is back with
    `inQty = 1`, `outQty = 1` for that period.
  - **Y** (AC-03): one tracked balance at `K09.01` qty 0, no ledger — assert one row, `quantity 0`.
  - **Z** (AC-05): ledger rows at `E01.01`, **no** `stock_balances` row — assert the `E01.01` row
    is present.
- `beforeAll` timeout `600_000` as the sibling suite does; `afterAll` closes the app.
- Run `pnpm --filter @erp/api test:e2e -- sku-breakdown-untracked` once against `main` (before
  T-01-01's change is merged into the working tree, or with the predicate temporarily commented
  out) and record in this ticket that AC-01/AC-02 go red there — the suite must be able to fail.
