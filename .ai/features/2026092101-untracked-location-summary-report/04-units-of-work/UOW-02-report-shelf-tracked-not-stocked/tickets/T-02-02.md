# T-02-02 — E2E: revenue detail "Mã vị trí" for a tracked empty shelf and a stopped one

## Context

The resolver's unit spec mocks the query builder, so the removal of `quantity > 0` (T-02-01)
is only *really* proven with Postgres evaluating the predicate list. The bug was reported on
"Chi tiết doanh thu theo hóa đơn và mặt hàng", so that is the report the suite drives; the other
three callers are covered by the shared unit spec (AC-08). New file, not an extension of
`invoice-item-revenue-detail.e2e-spec.ts` — keep suites per UoW.

## Implementation notes

- Boot exactly like `invoice-item-revenue-detail.e2e-spec.ts:34-41`: after `resetDatabase`,
  call `app.get(ReportTypeSyncService).onApplicationBootstrap()` or `/reports/invoices/search`
  will not know the report type.
- Fixture:
  - Warehouse: `POST /inventory/storages` on `seed.branchId` (non-main). Shelves `K09.01` and
    `E01.01` via `POST /inventory/locations` (type `SHELF`). No `item_storage_locations` rows —
    the case under test is "no preferred shelf".
  - Items: `POST /inventory/items` for **K** (AC-06) and **D** (AC-07).
  - Balances via the raw `stock_balances` upsert from
    `untracked-location-visibility.e2e-spec.ts:69-84`, all at quantity 0: K→`K09.01`;
    D→`A101`-equivalent (`E01.01`) and D→`K09.01`. Then
    `PATCH /inventory/stock/balances/tracking` `{ entries: [{ itemId: D, locationId: E01.01 }],
    isTracked: false }` — the real endpoint, as the sibling suite insists.
  - One paid `SALE` invoice on `seed.branchId` with one line each for K and D, using the
    `insertInvoice` / `insertLine` raw inserts from `invoice-item-revenue-detail.e2e-spec.ts:91-141`
    (the `session_id` / `staff_id` values there are what the report's joins tolerate). Add the
    `employee_profiles` row for the cashier as that suite does (`:49-53`) — the report resolves
    the cashier eagerly.
- Call `POST /reports/invoices/search` with `reportType: 'invoice-item-revenue-detail'`,
  `columns: ['invoiceCode', 'sku', 'locationCode', 'locationName', 'quantity']` and
  `filters.issuedAt` spanning the invoice date; expect `201`.
- Assertions:
  - **AC-06**: the row for K has `locationCode === 'K09.01'` (and `locationName` = the shelf
    name given at creation).
  - **AC-07**: the row for D has `locationCode === 'K09.01'` — the stopped `E01.01` pair is
    absent even though its quantity is the same 0 as the tracked one.
  - Sanity: re-track D→`E01.01` via the same PATCH and assert the row now reads
    `'E01.01, K09.01'` (the `joinShelves` order is by location code).
- Run the suite once with T-02-01's line restored (or before merging it) and record here which
  assertion goes red — AC-06 must fail on `main`, AC-07's exclusion must already pass.
