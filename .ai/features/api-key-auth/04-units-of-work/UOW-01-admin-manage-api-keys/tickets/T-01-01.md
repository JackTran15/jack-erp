# T-01-01 — ApiKeyEntity + migration

## Context
Bảng mới, org-scoped, PK uuid theo quy ước repo. Không lưu secret thô — chỉ `keyHash`
(A-03). `ipWhitelist` là jsonb string[] chấp nhận cả IPv4 đơn và CIDR (A-04). `branchIds`
nullable = không giới hạn chi nhánh (A-08). Soft-delete = thu hồi key, dùng
`@DeleteDateColumn()` theo pattern `SoftDeleteEntity` đã có trong repo.

## Implementation notes
- Cột: `id` (uuid), `organizationId`, `name`, `keyPrefix` (varchar ngắn, hiển thị được),
  `keyHash` (varchar, unique index — đường lookup chính của guard ở T-02-02, không phải
  PK), `roles` (text[]), `branchIds` (text[], nullable), `ipWhitelist` (jsonb),
  `createdAt`, `updatedAt`, `deletedAt`.
- Viết migration tay, không chạy `migration:generate` (feedback_handwrite_migrations).

## Done when
- [x] Entity + migration chạy `pnpm migration:run` sạch trên DB dev
- [x] `pnpm migration:revert` khôi phục đúng trạng thái trước đó
- [x] Không có cột nào cho phép lưu secret dạng plaintext

## Ghi chú bổ sung (G2 reopen — ADR-04)

Sau khi accept, G2 phải reopen: `roles` không đọc được ở đâu để phân quyền thật
(`PermissionGuard`/`RbacService` luôn tra `user_roles` theo `userId`, không bao giờ đọc
`request.user.roles`). Fix (ADR-04, 03-logical-design.md): mỗi key có một **shadow user**
thật. Migration + entity sửa lại thêm cột `user_id uuid NOT NULL REFERENCES users(id) ON
DELETE RESTRICT`; `roles` giữ nguyên kiểu `text[]` nhưng đổi nghĩa: giờ là `roles.id` thật,
chỉ dùng để tạo `user_roles` cho shadow user, không còn đọc lại ở `request.user`. Chi tiết
đầy đủ ở T-02-03.md/T-01-03.md.
