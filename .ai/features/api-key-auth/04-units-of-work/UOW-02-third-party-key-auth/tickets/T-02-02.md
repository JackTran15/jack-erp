# T-02-02 — ApiKeyAuthService.validate()

## Context
Chưa cache (UOW-03 sẽ bọc thêm `CacheService.getOrSet` quanh hàm này) — bản này query DB
trực tiếp mỗi lần gọi: đúng nghĩa "correctness trước, performance sau".

## Implementation notes
- `validate(rawKey: string, clientIp: string): Promise<ApiKeyValidationResult>` — dùng
  `hashApiKey()` (T-01-02) để tra `keyHash`; `findOne` trên entity có `@DeleteDateColumn`
  tự loại trừ row đã revoke, không cần tự thêm điều kiện `deletedAt IS NULL`.
- **Điều chỉnh so với draft ticket ban đầu**: bỏ `branch_denied` khỏi kết quả của
  `validate()` — chữ ký hàm chỉ nhận `(rawKey, clientIp)`, không có `branchId`, nên việc so
  khớp `X-Branch-Id` thuộc về guard (T-02-03), không phải service này. `validate()` chỉ trả
  `{ kind: 'not_found' } | { kind: 'ip_denied' } | { kind: 'ok', actor: ApiKeyActor }`, với
  `actor.branchIds` là `entity.branchIds ?? undefined` truyền thẳng, KHÔNG resolve danh sách
  chi nhánh ở đây (A-08's "kiểm bằng org membership" chuyển hẳn sang T-02-03).
- `ipMatch(ip, whitelistEntry)`: hỗ trợ IPv4 đơn và CIDR (A-04); không có entry IPv6; tự
  chuẩn hoá `::ffff:`-prefix mà Express có thể trả cho socket IPv4-mapped.
- `ApiKeyAuthService` đăng ký vào `api-key.module.ts` (providers + exports) để T-02-03 inject
  được — file này T-01-03 đã tạo, chỉ thêm vào.

## Done when
- [x] `kind: 'ok'` khi key đúng + IP trong whitelist (đơn + CIDR)
- [x] `kind: 'not_found'` khi key sai hoặc đã revoke (loại trừ tự động qua soft-delete)
- [x] `kind: 'ip_denied'` khi IP ngoài whitelist
- [x] Unit test không cần bootstrap Nest module (mock repository)

## Ghi chú bổ sung (sửa lại ở T-02-03, sau khi ticket này đã accept)

`actor.branchIds` KHÔNG còn là `entity.branchIds ?? undefined` như dòng 35 ở trên nữa.
Khi làm T-02-03 (guard), phát hiện: nếu để "guard tự tra danh sách chi nhánh" như note gốc
ở đây, phần query đó nằm ngoài biên mà T-03-01 sắp cache quanh `lookup()` — tức key không
giới hạn chi nhánh sẽ luôn tốn 1 query chi nhánh mỗi request dù cache hit, đi ngược US-06.
Đã sửa `lookup()` để tự resolve `branchIds` đầy đủ ngay tại đây (quay lại đúng
03-logical-design.md gốc: "branchIds — fully resolved"), thêm `Repository<BranchEntity>`
vào constructor. Chi tiết đầy đủ ở T-02-03.md.

## Ghi chú bổ sung 2 (G2 reopen — ADR-04)

`ApiKeyActor.roles` bị BỎ hẳn, thay bằng `ApiKeyActor.userId` (shadow user thật của key).
Lý do: `PermissionGuard`/`RbacService` chưa bao giờ đọc `request.user.roles` — chỉ tra
`user_roles` theo `userId` thật qua DB. `roles` trên `ApiKeyEntity` giờ chỉ có ý nghĩa lúc
tạo/sửa key (populate `user_roles` cho shadow user), không còn là thứ `validate()` trả về
nữa. Chi tiết đầy đủ ở 03-logical-design.md ADR-04 và T-02-03.md.
