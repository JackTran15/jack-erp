# T-03-02 — Nối invalidation thật

## Context
T-01-03 đã gọi `CacheService.invalidate` trong `afterUpdate`/`afterDelete` (no-op vì chưa
có gì trong cache lúc đó). Namespace khớp với T-03-01 (`API_KEY_CACHE_NAMESPACE` là 1 export
duy nhất, cả hai file cùng import — xem ghi chú ở T-03-01) nên không phải phần này sai.

## Implementation notes
**Bug thật phát hiện khi đọc lại đúng data flow (không phải chỉ giả định "chắc đúng rồi")**:
`afterUpdate(entity, actor)` tin `entity.keyHash` — nhưng `entity` ở đây do
`BaseCrudService.update()` dựng ra bằng cách tự gọi `this.getById(id, actor)` để nạp
`existing` TRƯỚC KHI merge/save. `getById()` (override ở T-01-03/T-01-05) đã `delete
entity.keyHash` để redact — nghĩa là tới lúc `afterUpdate` chạy, `entity.keyHash` LUÔN
`undefined`. Kết quả: mọi lần sửa key gọi `cache.invalidate('api-key', undefined)` — xoá
một cache key rác (`"...:undefined"`), không đụng tới cache thật của key vừa sửa. Cache cũ
(IP whitelist cũ, roles cũ...) vẫn sống nguyên tới hết TTL sau khi sửa.

Unit test cũ (`afterUpdate / afterDelete invalidate the cache`) không bắt được vì tự dựng
`{ id: 'key-1', keyHash: 'abc123' }` tay rồi gọi thẳng `afterUpdate` — bỏ qua hoàn toàn
đường đi thật qua `getById()`.

**Fix**: `afterUpdate` không tin `entity.keyHash` nữa — tự `findOne({ where: { id:
entity.id } })` lấy lại bản ghi thật, giống hệt pattern `afterDelete` đã dùng (vốn ĐÚNG vì
`afterDelete` chỉ nhận `id`, chưa bao giờ tin object).

## Done when
- [x] Sửa (`PATCH`) một key đang có trong cache → `afterUpdate` invalidate đúng `keyHash`
      thật (unit test mô phỏng đúng flow: `entity` truyền vào KHÔNG có `keyHash`, phải
      `findOne` lại mới lấy đúng)
- [x] Thu hồi (`DELETE`) một key đang có trong cache → không đổi, `afterDelete` vốn đã đúng
      từ T-01-03 (tự `findOne` bằng `id`, chưa bao giờ tin object truyền vào)
- Live-proof đầy đủ (Redis thật, gọi `validate()` trước/sau PATCH/DELETE) thuộc T-03-03 —
  ticket đó viết test dành riêng cho AC-07/AC-11/AC-12.

## Ghi chú bổ sung (G2 reopen — ADR-04)

Sau khi ticket này đã xong bug `keyHash`, G2 reopen thêm việc: `afterUpdate` giờ CŨNG phải
reconcile `user_roles` của shadow user (xoá hết + insert lại theo `fresh.roles`, không điều
kiện — làm mọi lần PATCH dù chỉ đổi `name`, tránh phải "nhớ" trên `this` xem payload gốc có
đổi `roles` hay không, đúng tinh thần tránh race đã áp dụng cho `create()`), và gọi
`RbacService.invalidateUserPermissions(shadowUserId, orgId)` — cache RBAC (namespace
`rbac`, TTL 300s) hoàn toàn tách biệt với cache `api-key` (TTL 60s) mà `afterUpdate` đã
invalidate từ trước; một PATCH đổi `roles` mà quên invalidate cache RBAC sẽ để quyền cũ
sống tới 5 phút dù key đã "cập nhật". `afterDelete` cũng deactivate shadow user
(`isActive: false`) và invalidate cùng cache RBAC, dù bản thân guard đã chặn ngay từ bước
tra key (cache `api-key` mất hiệu lực) — coi đây là phòng thủ thêm lớp, không phải cơ chế
chặn chính. Unit test cập nhật theo (`describe('afterUpdate')`/`describe('afterDelete')`
trong `api-key-crud.service.spec.ts`).
