# T-01-03 — HttpExceptionFilter preserves an exception-carried code

## Context
`HttpExceptionFilter.catch` (`apps/api/src/common/filters/http-exception.filter.ts:16-70`)
is the single chokepoint every thrown exception passes through before becoming a JSON
response. Today, inside the `exception instanceof HttpException` branch (lines 27-41), it
unconditionally synthesizes `code: \`HTTP_${status}\`` at line 32 — this is why
`AuthGuard`'s internal distinction never reaches the client today. Per
`03-logical-design.md` ADR-02, the filter should prefer an exception-carried `code` when
present, and this change is deliberately generic (not `AuthException`-specific) so any
future domain can opt in the same way without touching this file again.

This ticket has no code dependency on T-01-01/T-01-02 — it only needs to check for a generic
`code` property, not import `AuthErrorCode` — so it can proceed in parallel with them.

## Implementation notes
- In the `exception instanceof HttpException` branch, before building `body`, read
  `const explicitCode = (exception as { code?: unknown }).code;` and use it when it's a
  non-empty string:
  ```ts
  body = {
    code: typeof explicitCode === 'string' && explicitCode ? explicitCode : `HTTP_${status}`,
    message: ...,   // unchanged
    details: ...,   // unchanged
  };
  ```
- Do not touch the `else` branch (non-`HttpException`, `INTERNAL_ERROR`, lines 42-49) or the
  logging/response-shipping code below it (lines 51-70).
- Every existing `HttpException` throw site in the codebase has no `code` property, so this
  change is additive-only for all of them — verify by confirming the `HTTP_${status}`
  fallback is still exercised (see Done when).

## Done when
- [x] An `HttpException` instance with a truthy string `code` property produces that exact
      value in the response body's `code` field
- [x] An `HttpException` instance without a `code` property (or with `code: ''`) still
      produces `` `HTTP_${status}` `` — unchanged from today
- [x] The non-`HttpException` (`INTERNAL_ERROR`) branch is untouched
- [x] `pnpm --filter @erp/api build` succeeds
