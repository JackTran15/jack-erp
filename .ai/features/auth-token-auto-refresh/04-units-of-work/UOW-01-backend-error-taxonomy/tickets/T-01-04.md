# T-01-04 — Tests prove three distinct auth error codes reach the HTTP response body

## Context
No `auth.guard.spec.ts` exists today (confirmed by search of `apps/api/src/common`); an
`apps/api/test/e2e/auth.e2e-spec.ts` already exists and is the natural place to prove the
full guard→filter pipeline over a real HTTP round-trip, matching UOW-01's demo script
("curl three different broken-token scenarios, show three different code values").

## Implementation notes
- Unit (`apps/api/src/common/guards/auth.guard.spec.ts`, new): construct `AuthGuard` with
  mocked `Reflector`/`ConfigService`/`SessionStore`, and for each of the three failure
  subtypes, mock `jwt.verify` to throw the corresponding `jsonwebtoken` error class
  (`TokenExpiredError`, `JsonWebTokenError`, and separately `SessionStore.isSessionActive`
  resolving `false` for the revoked case) and assert `canActivate` rejects with an
  `AuthException` whose `.code` matches the expected `AuthErrorCode` value.
- E2E (`apps/api/test/e2e/auth.e2e-spec.ts`, extend): add 3 cases against a real protected
  endpoint — (a) an access token signed with a past `exp`, (b) a garbage/malformed bearer
  token, (c) a structurally valid, unexpired token whose session has been revoked (e.g. call
  `/auth/logout` first, then reuse the old access token) — asserting `response.status === 401`
  and `response.body.code` equals `AuthErrorCode.TOKEN_EXPIRED` /
  `AuthErrorCode.TOKEN_MALFORMED` / `AuthErrorCode.SESSION_REVOKED` respectively, and that the
  three values are pairwise distinct.
- Follow this suite's `apps/api/test/e2e/setup/global-setup.ts` conventions already used by
  the rest of `auth.e2e-spec.ts` (no new setup needed).

## Done when
