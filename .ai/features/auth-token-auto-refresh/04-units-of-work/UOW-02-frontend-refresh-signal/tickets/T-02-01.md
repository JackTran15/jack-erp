# T-02-01 — backoffice-web interceptor names the TOKEN_EXPIRED trigger

## Context
`apps/backoffice-web/src/lib/api-axios.ts:65-120` already runs a complete 401→refresh→retry
interceptor for every 401, unconditionally. Per `03-logical-design.md` Approach, this ticket
adds a named branch on `error.response?.data?.code` purely so the interceptor's log/trace
surface can say *why* it's refreshing — both branches must still call the exact same
refresh-and-retry logic that runs today. This is the AC-05/AC-08 non-negotiable: no 401
outside the new taxonomy may become worse off.

## Implementation notes
- Import `AuthErrorCode` from `@erp/shared-interfaces`.
- Inside the response-error handler, after confirming `error.response?.status === 401` and
  before the existing `__isRetry` / `isRefreshing` control flow (lines 71-98, all unchanged),
  read the code and branch on it, with both branches falling into the same subsequent logic:
  ```ts
  const authErrorCode = error.response?.data?.code as AuthErrorCode | undefined;
  if (authErrorCode === AuthErrorCode.TOKEN_EXPIRED) {
    // access token expired — refresh-and-retry below runs exactly as today
  }
  // else: no code, or a code this branch doesn't special-case yet (SESSION_REVOKED,
  // TOKEN_MALFORMED, or a legacy uncoded 401) — still falls through to the same
  // refresh-and-retry logic below (AC-05 regression guard, non-negotiable)
  ```
- Do not change the coalescing (`isRefreshing`/`failedQueue`), the `__isRetry` guard, or the
  terminal clear-session-and-redirect path — none of those lines move.
