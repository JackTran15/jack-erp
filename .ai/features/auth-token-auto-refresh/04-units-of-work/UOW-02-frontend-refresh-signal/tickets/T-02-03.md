# T-02-03 — Regression tests for the fallback, revoked-session, and second-401 paths

## Context
Both apps already have vitest-based `.test.ts` files co-located with the source they cover
(e.g. `apps/backoffice-web/src/lib/print/render-voucher-html.test.ts`,
`apps/pos-web/src/lib/page-libs/checkout/checkoutValidation.test.ts`), run via
`npx vitest run <path>`, despite each app's `package.json` `"test"` script being a
`echo test` stub (per root `CLAUDE.md`: "only @erp/api has real tests; the web apps echo
'test'" — the vitest files are a pre-existing, already-working exception to that, not a new
test-runner setup this ticket introduces). Follow that exact pattern; do not add a vitest
config or change either app's `package.json`.

This ticket is the authoritative proof of the AC-05/AC-06/AC-07/AC-08 regression guarantees
that T-02-01/T-02-02 must not violate.

## Implementation notes
- For each app, mock the axios instance's response interceptor rejection path directly (no
  network) with these cases:
  1. 401, body `{}` (no `code`) → refresh is attempted (AC-05).
  2. 401, body `{ code: "9999999" }` (unrecognized) → refresh is attempted (AC-05).
  3. 401, body `{ code: "4014002" }` (`SESSION_REVOKED`) → refresh is attempted first, and
     when the refresh call itself rejects, the existing clear-session-and-redirect path
     fires (AC-08) — and the original error's `code` value is not stripped or overwritten by
     the interceptor before it propagates (AC-07: "preserved unchanged in the structure the
     layer already carries").
  4. A request already marked retried (`__isRetry`/`_retry: true`) receiving another 401 →
     clears session and redirects immediately, with no second refresh call (AC-06).
- backoffice-web: stub `getRefreshToken`/`persistRefreshResponse`/`clearSession` from
  `./auth-storage` and `getAccessToken`/`clearAccessToken` from `./access-token` (already
  separate modules the interceptor imports) rather than reaching into `localStorage`
  directly.
- pos-web: stub `localStorage` access for `access_token`/`refresh_token` directly, matching
  how `tryRefreshToken` reads/writes them today.
