# T-01-01 — ItemStorageLocationService.validateAndAssignBatch

## Context

Replaces the per-movement loop at `stock-ledger.service.ts:264-271` that calls
`validateAndAssignByLocation(itemId, locationId, actor)` once per line. Read the existing
`validateAndAssignByLocation` (line ~93) and `validateAndAssign` (line ~31) first — the new
batch method must reproduce their exact semantics, just with the reads/writes batched.

## Implementation notes

- New public method on `ItemStorageLocationService`:
  `validateAndAssignBatch(items: { itemId: string; locationId: string }[], actor: ActorContext): Promise<void>`.
- Step 1 — one query: `locationRepo.find({ where: { id: In(distinctLocationIds), organizationId, ...(branch scope) }, relations: { storage: true } })`,
  build a `Map<locationId, LocationEntity>`.
- Step 2 — in memory: for each `{itemId, locationId}`, look up the location; if missing,
  silently skip (matches today's `return` in `validateAndAssignByLocation` — do **not**
  throw here, that would be a behaviour change). If `location.isUnassigned`, skip (AC-05).
  Otherwise, keep the **first** occurrence per `itemId` (dedupe with a `Map`, first-wins —
  A-02) as `{ itemId, storageId: location.storageId, locationId }`.
- Step 3 — one query: `islRepo.find({ where: pairs.map(p => ({ itemId: p.itemId, storageId: p.storageId, organizationId })) })`
  (TypeORM OR-array where) to find which pairs already have a mapping.
- Step 4 — one query: bulk-insert the pairs with no existing mapping via
  `.createQueryBuilder().insert().values(toInsert).orIgnore().execute()`
  (`ON CONFLICT (item_id, storage_id) DO NOTHING` — AC-06: never overwrites an existing
  valid mapping).
- Step 5 — unbatched, unchanged: for each `existing` mapping found in step 3, re-check its
  `locationId` against the Map from step 1; if no longer valid, `islRepo.update(...)` it to
  the new target (the existing "repair" `logger.warn` stays as-is).
- Keep `validateAndAssignByLocation` and `validateAndAssign` in place, untouched —
  `recordMovement` (single-movement path) still calls them directly; only
  `recordBatchMovements`'s loop is replaced (that wiring is T-01-02).
