# T-01-02 — Bulk-insert ledger entries + bulk-upsert stock_balances

## Context

Depends on T-01-01. Rewrites `recordBatchMovements`'s pre-check loop
(`stock-ledger.service.ts:264-271`) to call `pslService.validateAndAssignBatch(...)` once,
and rewrites `writeBatchMovements` (`:701-733`) and `upsertBalance` (`:750-802`) to stop
looping per movement. `assertStoragesActive` (`:674-699`) is already batched — leave it
as-is (AC-04).

## Implementation notes

- `recordBatchMovements`: replace the `for (const params of movements) { ... validateAndAssignByLocation ... }`
  loop with:
  ```ts
  const toValidate = movements
    .filter(m => !m.skipLocationAssignment)
    .map(m => ({ itemId: m.itemId, locationId: m.locationId }));
  if (toValidate.length) await this.pslService.validateAndAssignBatch(toValidate, /* actor from movements[0].actorContext */);
  ```
- `writeBatchMovements`:
  1. Build `rows` (same shape `manager.create` builds today) for every movement, via
     `deriveCostFields`.
  2. `const result = await manager.createQueryBuilder().insert().into(StockLedgerEntryEntity).values(rows).execute();`
  3. **Defensive guard (A-01):** `if (result.identifiers.length !== rows.length) throw new Error('stock ledger bulk insert returned a mismatched identifier count');`
     before zipping — fail loudly inside the transaction rather than silently mismatch ids.
  4. `savedEntries = rows.map((r, i) => ({ ...r, id: result.identifiers[i].id }))`.
  5. Aggregate deltas: `Map<'orgId:itemId:locationId', { organizationId, branchId, itemId, locationId, quantity, createdBy }>`,
     summing `Number(m.quantity)` per key (keep the **first** `branchId`/`createdBy` seen
     for that key — they're the same actor/branch across one batch in practice).
  6. Run the bulk UPSERT (raw SQL via `manager.query`, parameterized — build the multi-row
     `VALUES` list from the aggregated map, do not string-concat quantities/ids):
     ```sql
     INSERT INTO stock_balances
       (id, organization_id, branch_id, item_id, location_id, quantity, last_movement_at, is_tracked, created_by)
     SELECT gen_random_uuid(), v.organization_id, v.branch_id, v.item_id, v.location_id, v.quantity, now(), true, v.created_by
     FROM (VALUES ...) AS v(organization_id, branch_id, item_id, location_id, quantity, created_by)
     ON CONFLICT (organization_id, item_id, location_id)
     DO UPDATE SET
       quantity = stock_balances.quantity + EXCLUDED.quantity,
       last_movement_at = EXCLUDED.last_movement_at,
       is_tracked = true
     RETURNING item_id, location_id, quantity;
     ```
  7. For every returned row with `quantity < 0`, emit one `logger.warn` naming
     item/location/resulting quantity (A-03 — same log shape, aggregated granularity).
- Do **not** touch `recordMovement` (single-movement path) or `upsertBalance`'s existing
  per-call usage from `recordMovement` — only `writeBatchMovements`'s internals change.
- `publishMovementEvents` call sites and timing (after commit) stay exactly as-is.
