# T-01-01 — Trim lines/item/location joins from the Goods Receipt search handler

## Context
`SearchGoodsReceiptsV2Handler.execute()` builds its row query with an explicit `QueryBuilder`
(`createQueryBuilder("gr")`), so `GoodsReceiptEntity.lines`'s `eager: true` never fires here — the
`.leftJoinAndSelect("gr.lines", "lines")`, `.leftJoinAndSelect("lines.item", "lineItem")`, and
`.leftJoinAndSelect("lines.location", "lineLocation")` calls (`search-goods-receipts-v2.handler.ts:50-52`)
were added by hand to keep row shape parity with the old `find()`-based list. Removing them is a pure
deletion — no new query technique needed, and the totals query (`buildQuery` + `TOTAL_AMOUNT_SUBQUERY`)
already never joins `lines`, so it's untouched.

## Implementation notes
- Delete the three `leftJoinAndSelect` lines only; keep `.leftJoinAndSelect("gr.provider", "provider")`
  and `.leftJoinAndSelect("gr.location", "location")`.
- Update the comment above the joins (`:44-46`) — it currently says the joins exist "so the detail panel
  and view dialog rely on `lines`"; that's no longer true for the list response after this change.
- No DTO change — `data[]` rows are still `GoodsReceiptEntity[]`, just without a populated `lines`
  relation (TypeORM leaves it `undefined` when not joined, which serializes as absent, not `[]`).
- `attachCounterparties`/`attachPurchasingEmployees` calls are unaffected — they don't touch `lines`.

## Done when
- [x] The three `lines`/`lines.item`/`lines.location` `leftJoinAndSelect` calls are removed from the
      row query
- [x] `provider` and `location` joins are still present and unchanged
- [x] `search-goods-receipts-v2.handler.spec.ts` (existing) is updated to assert the response rows do
      not carry a `lines` field
- [x] `pnpm --filter @erp/api test -- search-goods-receipts-v2` passes

## Deviation from plan
The ticket/design didn't account for `PurchaseOrdersPage.tsx`'s list "Tổng tiền" column
(`orderTotal(row)`), which computed each row's total client-side from `row.lines` — the one place
outside the DetailPanel/barcode toolbar that read `lines` off a list row. Once `lines` is dropped
(`undefined`, not `[]`), that render function throws on every row, crashing the whole list. Added a
small additive fix in this ticket: a third, cheap query (`gr.id IN (:...ids)`, same
`TOTAL_AMOUNT_SUBQUERY` as the footer) attaches a transient `totalAmount` to each row so the column
works without joining `lines`/`item`/`location`. See `goods-receipt.entity.ts`'s new transient
`totalAmount` field and the "attaches each row's own totalAmount" spec case. T-02-01 carries the
identical fix for Goods Issue's `issueTotal`; Transfer Order has no such column.
