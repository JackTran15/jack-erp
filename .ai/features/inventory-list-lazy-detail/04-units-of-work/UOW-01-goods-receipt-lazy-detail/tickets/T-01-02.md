# T-01-02 — Add paginated GET /goods-receipts/:id/lines endpoint

## Context
New sub-resource, additive — follows the existing `GET /:id/print-payload` / `GET /:id/export`
convention on the same controller (`goods-receipt.controller.ts:91-115`). Two steps per request:
1. An existence + org/branch-scope check equivalent to today's `findOrFail`, but via
   `receiptRepo.findOne({ where: { id, organizationId, ...(branchId ? { branchId } : {}) },
   loadEagerRelations: false })` — see ADR-02 in `03-logical-design.md`. 404
   (`NotFoundException`) if not found. This deliberately does **not** reuse the private `findOrFail`
   method, because that method's eager `lines` load is relied on by `getPrintPayload` and by
   `TransferOrderService.applyDeltaToLines` (see `03-logical-design.md` ADR-01) — this ticket must not
   touch it.
2. A paginated query directly against `GoodsReceiptLineEntity`: `where: { goodsReceiptId: id,
   organizationId }`, `order: { createdAt: "ASC" }`, `skip`/`take` from `page`/`pageSize`, plus a
   `count()` with the same `where`. `GoodsReceiptLineEntity.item`/`.location` stay `eager: true`
   (`goods-receipt-line.entity.ts:65-71`) — untouched, so each returned line already carries its item
   and location detail.

## Implementation notes
- Route: `GET goods-receipts/:id/lines`, same guards/permission as the existing `GET :id`
  (`@RequirePermission('goods_receipt.read')`, `@RequireBranchScope()`).
- Query params: reuse `PaginationQueryDto` (`apps/api/src/modules/crud/dto/pagination-query.dto.ts`) —
  it already has `page`/`pageSize` with the right defaults/validation (default 1 / default 20, max 100);
  ignore its other optional fields (`search`, `filters`, etc.) rather than adding a new DTO.
- Response shape: `{ items, page, pageSize, hasMore, total }` — see `03-logical-design.md` Contracts
  section for the exact shape and field semantics (`hasMore = page * pageSize < total`).
- A document with zero lines returns `{ items: [], page, pageSize, hasMore: false, total: 0 }` — not an
  error (AC-08).

## Done when
- [x] `GET /goods-receipts/:id/lines?page=&pageSize=` returns paginated lines with `item`/`location`
      populated per line
- [x] The existence/scope check uses `loadEagerRelations: false` (or equivalent lean query), not
      `findOrFail` — confirmed by reading the diff, not just by test output
- [x] 404 for a nonexistent id or one outside the actor's org/branch scope
- [x] A zero-line document returns 200 with `items: []`, `hasMore: false`, `total: 0`
- [x] `hasMore` is correctly `false` on the last page and `true` otherwise

Automated test coverage for these behaviors is written in T-01-05 (regression suite), per that
ticket's explicit ownership of `goods-receipt.service.spec.ts` assertions for this endpoint; this
ticket's behavior was verified by code review of `getLines()`/`getById` route wiring.
