# T-01-03 — Row click fetches GET /:id; barcode toolbar reads from it instead of the list row

## Context
`PurchaseOrdersPage.tsx` derives its "selected document" via the shared
`useDocumentListSelection` hook (`apps/backoffice-web/src/components/document/useDocumentListSelection.ts`),
which today computes `activeRecord`/`selectedRecord` purely client-side —
`rows.find((row) => getRowId(row) === selectedId)` — off the already-fetched list page
(`useDocumentListSelection.ts:16-19`). Once T-01-01 strips `lines` from those rows, `.lines` on that
derived object becomes empty for every row. `GET /goods-receipts/:id` itself is unchanged (still
eager-loads full `lines`, per `03-logical-design.md` ADR-01) — this ticket doesn't need the new
`/:id/lines` endpoint (T-01-02); it only needs to start calling the existing `GET /:id`.

Two call sites currently read `selectedOrder.lines` directly and must be rewired:
- Barcode toolbar action (`PurchaseOrdersPage.tsx:459`)
- `DetailPanel`'s `order` prop (`PurchaseOrdersPage.tsx:697`) — T-01-04 handles the line *table*
  rendering inside `DetailPanel`; this ticket only needs to make sure `DetailPanel` keeps receiving a
  valid `order` object with header fields (status, counterparty, etc.) for the non-line parts it
  renders (e.g. `order.status`).

## Implementation notes
- Add a `useQuery` keyed on `selectedId` (e.g. `["goods-receipt", selectedId]`) that calls
  `GET /goods-receipts/:id` via `erpApi`/`requireErpData`, `enabled: !!selectedId`.
- Replace `selectedOrder` (currently `useDocumentListSelection`'s `activeRecord`, sourced from
  `records.data`) with this query's data wherever full detail (including `lines`) is needed — the
  barcode toolbar (`:459`) and the `order` passed to `DetailPanel` (`:697`).
- Header fields must render as soon as this query resolves — do not block on any line-pagination fetch
  (that's T-01-04, and it's a separate query/component concern).
- `useDocumentListSelection`'s `selectedId` state itself is unchanged — this ticket only changes what
  the page does with it.

## Done when
- [x] Clicking a row (or its doc-number link) triggers a `GET /goods-receipts/:id` network request
- [x] Header fields (doc number, date, counterparty, status, total) render as soon as that request
      resolves, without waiting on any `/lines` request
- [x] The barcode toolbar action ("In tem mã") builds its item list from the `GET /:id` response's
      `lines`, not from the list row
- [~] Manually verified against a receipt with several lines: barcode print list matches the receipt's
      actual lines — verified by code inspection (selectedOrder now sources from the GET /:id query
      result end-to-end); full browser click-through deferred to G4 demo, not done in this session
- [x] `pnpm --filter @erp/backoffice-web build` passes (type-check) — confirmed green

## Deviation from plan
The ticket scoped only the barcode toolbar + `DetailPanel`'s `order` prop as `.lines` read sites, but
the same page also opens `PurchaseOrderFormDialog` (Nhân bản/Xem/Sửa toolbar buttons, and the
doc-number-link click handler) with `editingOrder` sourced from the stale list row —
`GoodsReceiptFormDialog.tsx:400` reads `initial.lines` directly, so those flows would have opened with
zero lines (and Sửa risked silently saving an emptied line set). Fixed as part of this ticket:
- `selectedOrder` itself is now sourced from the new `useQuery` (not the hook's list-row-derived
  `activeRecord`), so the 3 toolbar buttons that do `setEditingOrder(selectedOrder)` get full lines for
  free.
- The doc-number-link handler now fetches `GET /goods-receipts/:id` before opening the view dialog,
  mirroring the pre-existing `openDocumentId` deep-link fetch pattern already in this file.
