# T-02-01 — Trim lines/item/location joins from the Goods Issue search handler

## Context
Same situation as Goods Receipt (T-01-01): `SearchGoodsIssuesV2Handler.execute()` builds its row query
via an explicit `QueryBuilder` (`createQueryBuilder('gi')`), so `GoodsIssueEntity.lines`'s
`eager: true` never fires here — the `.leftJoinAndSelect('gi.lines', 'lines')`,
`.leftJoinAndSelect('lines.item', 'lineItem')`, `.leftJoinAndSelect('lines.location', 'lineLocation')`
calls (`search-goods-issues-v2.handler.ts:61-63`) were added by hand for row-shape parity with the old
`find()`-based list. Removing them is a pure deletion.

## Implementation notes
- Delete the three `leftJoinAndSelect` lines only; keep `.addSelect('targetBranch')`,
  `.leftJoinAndSelect('gi.provider', 'provider')`, `.leftJoinAndSelect('gi.reasonRef', 'reasonRef')`,
  and `.leftJoinAndSelect('gi.location', 'location')`.
- Update the comment above the joins (`:50-52`) — it currently claims the joins exist because "the
  detail panel and view dialog rely on `lines`"; no longer true for the list response.
- `buildQuery`'s `targetBranch` join and `TOTAL_AMOUNT_SUBQUERY`-based totals query are untouched —
  neither ever joined `lines`.

## Done when
- [x] The three `lines`/`lines.item`/`lines.location` `leftJoinAndSelect` calls are removed from the
      row query
- [x] `provider`, `reasonRef`, `location`, `targetBranch` joins are still present and unchanged
- [x] `search-goods-issues-v2.handler.spec.ts` (existing) is updated to assert response rows do not
      carry a `lines` field
- [x] `pnpm --filter @erp/api test -- search-goods-issues-v2` passes — 9/9

## Deviation from plan
Same `Tổng tiền` list-column regression as T-01-01 (see that ticket's Deviation note):
`GoodsIssuePage.tsx`'s `issueTotal(row)` summed `row.lines` client-side. Applied the identical fix —
a third `gi.id IN (:...ids)` query reusing `TOTAL_AMOUNT_SUBQUERY`, attaching a transient `totalAmount`
to each row via `goods-issue.entity.ts`.
