# T-03-01 — Bypass TransferOrderEntity's eager lines/item in list() only, via loadEagerRelations:false

## Context
`TransferOrderEntity.lines` (`transfer-order.entity.ts:97-101`) and, transitively,
`TransferOrderLineEntity.item` (`transfer-order-line.entity.ts:53-55`) are `eager: true`. Unlike GR/GI's
search handlers, `TransferOrderService.list()` (`transfer-order.service.ts:451-472`) calls
`this.toRepo.findAndCount({ where, skip, take, order })` (`:465-470`) — a plain `Repository` call, which
*does* trigger eager loading. Per ADR-02 in `03-logical-design.md`, the fix is a single added option,
`loadEagerRelations: false`, on that one call — confirmed present and inherited by `FindManyOptions` in
the installed `typeorm@0.3.28`.

**This is the highest-risk ticket in the feature.** `TransferOrderEntity`'s `find*()` methods have
several other callers that must keep receiving eager `lines`/`item` completely unchanged:
- `findOrFail` (`:1718-1725`, used by `getById`, itself used by `getPrintPayload` at `:285-290` and,
  cross-service, by `applyDeltaToLines`'s fetcher functions at `:1476` and elsewhere)
- `getByCode` (`:441-449`)
- `listIssuable` (`:480-...`), `listImportable`

None of these call `list()` — this ticket touches only `list()`'s own `findAndCount()` call, so none of
them are affected by construction, but the Done-when below requires proving it, not just asserting it.

## Implementation notes
- Add `loadEagerRelations: false` to the existing `findAndCount({ where, skip, take, order })` call
  (`:465-470`). Do not change `where`, `skip`, `take`, or `order` — this must be a single added key.
- Do not touch `TransferOrderEntity.lines`'s or `TransferOrderLineEntity.item`'s `eager: true`
  declarations — explicitly out of scope (`00-intent.md`).
- Do not refactor `findOrFail`, `getByCode`, `listIssuable`, or `listImportable` — they are untouched by
  this ticket.
