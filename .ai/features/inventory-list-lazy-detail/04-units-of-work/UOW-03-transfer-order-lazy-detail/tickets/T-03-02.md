# T-03-02 — Add paginated GET /inventory/transfer-orders/:id/lines endpoint

## Context
Mirrors T-01-02/T-02-02 for Transfer Order. New sub-resource, additive, alongside the existing
`GET :id/print-payload` (`transfer-order.controller.ts:405-...`). Two steps:
1. Existence + org/branch-scope check via `toRepo.findOne({ where: { id, organizationId },
   loadEagerRelations: false })` plus the existing `assertParticipantBranch` check
   (`transfer-order.service.ts:1727-1738`) for branch participation. 404 if not found or out of scope.
   Does **not** reuse `findOrFail` — that method's eager `lines` load is relied on by `getPrintPayload`
   and `applyDeltaToLines` (ADR-01 in `03-logical-design.md`); this ticket must not touch it.
2. Paginated query directly against `TransferOrderLineEntity`: `where: { transferOrder: { id },
   organizationId }` (or the FK column directly, matching this entity's join-column convention —
   `transfer-order-line.entity.ts:49-51` uses a relation, not a bare `transferOrderId` column, so check
   the actual column name before writing the query), `order: { createdAt: "ASC" }`, `skip`/`take` from
   `page`/`pageSize`, plus `count()`. `TransferOrderLineEntity.item` stays `eager: true`
   (`transfer-order-line.entity.ts:53-55`) — each returned line already carries item detail.

## Implementation notes
- Route: `GET inventory/transfer-orders/:id/lines`, same guard/permission as the existing `GET :id`
  (`@RequirePermission("inventory.transfer.read")`).
- Query params: reuse `PaginationQueryDto` — `page`/`pageSize` with existing defaults/validation.
- Response shape: `{ items, page, pageSize, hasMore, total }` — see `03-logical-design.md` Contracts.
- A document with zero lines returns `{ items: [], page, pageSize, hasMore: false, total: 0 }`.
- Note `TransferOrderLineEntity` has no `location`/`storageId` eager relation the way GR/GI lines do —
  only `sourceLocationId` (`transfer-order-line.entity.ts:57-63`, a plain nullable column, no eager
  join); don't invent one — mirror whatever shape `DetailPanel` already renders today
  (`TransferOrdersPage.tsx:612-660` reads `line.sourceStorageId ?? order.sourceStorageId`).

## Done when
- [x] `GET /inventory/transfer-orders/:id/lines?page=&pageSize=` returns paginated lines with `item`
      populated per line
- [x] The existence/scope check uses `loadEagerRelations: false` (or equivalent lean query) plus branch
      participation, not `findOrFail`
- [x] 404 for a nonexistent id or one outside the actor's branch participation
- [x] A zero-line document returns 200 with `items: []`, `hasMore: false`, `total: 0`
- [x] `hasMore` is correctly `false` on the last page and `true` otherwise

Automated coverage written in T-03-05 (this UoW's regression ticket), mirroring T-01-02/T-02-02.

## Note
`TransferOrderLineEntity` does have a bare `transferOrderId` column after all (`transfer-order-line.entity.ts:24-25`)
— the ticket's caution "check the actual column name before writing the query" was warranted but the
premise that it "uses a relation, not a bare column" didn't hold; used `transferOrderId` directly,
matching GR's pattern. Also has `organizationId` and `createdAt` (order by `createdAt ASC`, matching GR).
No dedicated `TransferOrderLineEntity` repository was injected into `TransferOrderService`, so used
`this.toRepo.manager.findAndCount(...)`, matching the pattern already used in this service
(`manager.delete(TransferOrderLineEntity, ...)`) and T-02-02's identical choice for Goods Issue.
