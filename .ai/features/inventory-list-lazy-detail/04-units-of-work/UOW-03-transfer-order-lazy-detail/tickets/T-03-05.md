# T-03-05 — Regression coverage — list bypass, new endpoint, every other TO caller unaffected

## Context
Closes out UOW-03 with the widest regression sweep in the feature, matching its `risk: high` rating:
`TransferOrderEntity`'s `eager: true` is shared by every `find*()` caller, and this UoW is the one that
adds a scoped bypass for it. Proving the bypass didn't leak beyond `list()` is the point of this ticket.

## Implementation notes
- Add/update `transfer-order.service.spec.ts` assertions:
  - `list()` response rows have no `lines`/`item` populated.
  - New lines method: paginated happy path, 404 for unknown/out-of-scope id, empty-lines document
    returns `hasMore: false`/`total: 0`, `hasMore` toggles correctly across a page boundary.
- Re-run (unmodified) the existing spec cases for `findOrFail`/`getById`, `getByCode`, `listIssuable`,
  `listImportable`, and `applyDeltaToLines` (the quantity-delta edit flow) — confirm every one of them
  still returns/relies on eager `lines`/`item` exactly as before T-03-01.
- Cross-reference with T-01-05/T-02-05: this ticket only re-runs the TO-side half of the
  `applyDeltaToLines` regression (the TO service's own logic); the GR/GI-side half
  (`goodsReceiptService.getById`/`goodsIssueService.getById` still returning full `lines`) is proven by
  those tickets' own suites.
- Do not modify existing `getPrintPayload`/`getById`/export-related spec assertions.
