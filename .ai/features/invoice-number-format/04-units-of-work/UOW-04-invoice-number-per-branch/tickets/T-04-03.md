# T-04-03 — Sửa test AC-07 (đảo ngược) + test AC-17

## Context

T-01-05 (`done`) có sẵn một khối test cho AC-07 khẳng định đúng hành vi cũ: "gọi cấp số hai
lần với hai `branchId` khác nhau, cùng `organizationId` → `2608210001` và `2608210002`... chỉ
có một hàng `document_number_counters` được tạo". A-10/ADR-07 đảo ngược điều đó. Ticket này sửa
**đúng khối test của AC-07** trong `document-numbering.service.spec.ts` (đường trả/đổi qua
`generate()`) và khối tương ứng trong `next-document-number.step.spec.ts` (đường bán qua saga,
ADR-05 — hai đường khác nhau, sửa một không nói gì về đường kia) — không đụng các `it()` khác
của AC-02/03/05/06/08/09 trong cùng file.

## Implementation notes

- AC-16 (đối chiếu cuối ngày liên tục): xen kẽ hoá đơn của hai chi nhánh trong cùng ngày (branch
  A, branch B, branch A, branch A, branch B — mô phỏng đúng kiểu xen kẽ trong ảnh QA #26), rồi
  đọc counter/`document_number_rules` theo riêng `branchId` A → khẳng định dải giá trị counter
  của A là `1..3` liên tục, không phụ thuộc vào việc B đã chen vào giữa.

- AC-07 (sửa lại): cấp số hai lần với hai `branchId` khác nhau, cùng `organizationId`, cùng
  ngày → cả hai đều là `<date>0001`; khẳng định có **hai** hàng `document_number_counters` được
  tạo (một mỗi chi nhánh, `ruleId` khác nhau) và **hai** hàng `document_number_rules` (rule
  theo chi nhánh vừa nhân bản), không phải một.
- AC-17: dựng sẵn counter org-wide ở giá trị N > 0 cho `resetKey` hôm nay, gọi `generate`/
  `preview` lần đầu cho một `branchId` chưa từng có rule → rule theo chi nhánh được tạo, số đầu
  tiên trả về > N (fast-forward có tác dụng), và không trùng bất kỳ số 1..N nào.
- Giữ nguyên fake timer pattern đã có trong T-01-05 (`jest.useFakeTimers().setSystemTime(...)`,
  khôi phục ở `afterEach`).
- Test qua `next-document-number.step.spec.ts` cho đường đơn bán (dùng
  `mint-document-number.ts`'s `resolveActiveRule` — không đổi, chỉ cần rule theo chi nhánh đã
  tồn tại từ trước khi bước này chạy, nên fixture setup gọi `preview()` thật hoặc insert rule
  trực tiếp trước khi gọi `mintDocumentNumber`) và `document-numbering.service.spec.ts` cho
  đường đơn trả (gọi thẳng `generate()`).

## Note (scope correction — written during implementation)

T-04-02 already fixed the AC-07 block in `document-numbering.service.spec.ts` (the
return/exchange path via `generate()`/`preview()`) and already added an AC-17 test in that
same file, both inside the "branch-scoped INVOICE/RETURN rule cloning (T-04-02)" describe
block. That part of the original scope above (Context/Implementation notes for AC-07 and
AC-17 on the `document-numbering.service.spec.ts` side) was already done before this ticket
started — this ticket did not redo it. What was still genuinely open and is what this
ticket actually did:

1. `next-document-number.step.spec.ts` (SALE path via `NextDocumentNumberStep`/
   `mintDocumentNumber`, ADR-05 — a separate mock harness from the service spec) still had
   the old, reversed AC-07 test asserting two branches share one org-wide counter. Replaced
   it with a test asserting each branch resolves and locks against its OWN branch-scoped
   rule (both mocked as already-resolved, per A-10/ADR-07 — `mint-document-number.ts` itself
   is unchanged, it never creates rules), each independently minting `2608210001`.
2. Added one AC-16 test to `document-numbering.service.spec.ts`, inside the existing T-04-02
   describe block, reusing its in-memory rule/counter store: interleaves branch A / branch B
   / branch A calls to `generate()` and asserts branch A's own counter row lands on `2`
   (contiguous 1→2), unaffected by branch B's call landing in between. (`preview()` does not
   increment the counter — read-only — so this test uses `generate()`, unlike the sibling
   AC-07 test in the same block which uses `preview()` for that same reason: it does not
   need to advance state.)
