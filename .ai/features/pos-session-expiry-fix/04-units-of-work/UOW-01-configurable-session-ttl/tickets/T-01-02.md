# T-01-02 — Tests prove issued/rotated tokens carry the configured TTL

## Context
`auth.service.spec.ts` already exists and presumably exercises `login`/`refresh`/
`switchBranch`/`exchangeHandoffCode` for their existing behavior — extend it rather than
duplicating its setup. Read it first to match its existing mocking style for
`ConfigService`, `SessionStore`, and `jwt`.

## Implementation notes
- Default-TTL case: with `ConfigService.get` mocked to fall through to its default
  argument (i.e. no `JWT_ACCESS_TTL`/`JWT_REFRESH_TTL` override registered), decode the
  `accessToken`/`refreshToken` returned by `login()` and assert `exp - iat === 86400` /
  `2592000` respectively.
- Override case: mock `ConfigService.get` to return a distinct value (e.g. `1800`) for
  `JWT_ACCESS_TTL` and assert the issued access token's `exp - iat` equals it — proves the
  override path, not just that a default exists.
- Rotation case: call `refresh()` with a valid refresh token/session and assert the
  newly issued tokens carry the same TTL behavior as `login()` — do not assume `refresh()`
  reuses `login()`'s code path; it has its own call sites (`auth.service.ts` ~165-189).
- Cover `switchBranch()` and `exchangeHandoffCode()` too — they're separate call sites
  (~220-246, ~332-353) with their own risk of a missed rename in T-01-01.

## Done when
- [x] A default-TTL test and an override test both pass for `login()`
- [x] `refresh()`, `switchBranch()`, and `exchangeHandoffCode()` each have at least one
      test asserting the issued token's `exp - iat` matches the configured TTL
- [x] `pnpm --filter @erp/api test -- auth.service.spec.ts` passes
