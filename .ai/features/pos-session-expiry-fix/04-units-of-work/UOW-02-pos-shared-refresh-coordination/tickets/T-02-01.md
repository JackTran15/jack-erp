# T-02-01 — Extract shared tryRefreshToken/refreshOnce into token-refresh.ts

## Context
`http.ts:13-55` and `api-axios.ts:47-81` each hold a near-identical
`tryRefreshToken`/`refreshOnce` pair. Both read `POS_REFRESH_TOKEN_KEY` from
`localStorage`, POST to `/auth/refresh`, and write the response's `accessToken`/
`refreshToken` back to `localStorage`. They differ only in HTTP client (`fetch` vs
`axios`) and in failure handling: `api-axios.ts`'s `catch` clears both tokens on any
thrown error; `http.ts`'s does not — only its `!res.ok` branch clears them, leaving a
thrown/network-error case with stale tokens still in storage.

## Implementation notes
- New file `apps/pos-web/src/lib/common/token-refresh.ts` exporting `refreshOnce():
  Promise<boolean>`, backed by module-level `refreshPromise` (single-flight, same shape as
  today's two copies) and an internal `tryRefreshToken()` using `fetch` (no need for an
  axios dependency in a lib module both clients — one fetch-based, one axios-based — will
  import).
- On any failure path (non-ok response, thrown/network error, or a response missing
  `accessToken`), clear both `POS_ACCESS_TOKEN_KEY` and `POS_REFRESH_TOKEN_KEY` from
  `localStorage` and return `false` — this is `api-axios.ts`'s stricter behavior, applied
  uniformly; document the change from `http.ts`'s current inconsistent behavior in the
  commit message.
- Do not add a "no refresh token in storage" special case beyond what's already there
  (`if (!refreshToken) return false`) — both originals already handle this identically.

## Done when
- [x] `token-refresh.ts` exports `refreshOnce`, used by nothing yet (wired in T-02-02/03)
- [x] Two concurrent calls to `refreshOnce()` share one in-flight promise (same guarantee
      the two originals already provided individually)
- [x] Any refresh failure clears both tokens, regardless of whether the failure was a
      non-ok HTTP response or a thrown error

## Post-acceptance correction (found while implementing T-02-03)
This ticket's own implementation notes chose `fetch` for the shared module ("no need for an
axios dependency"). That was wrong: `api-axios.ts`'s existing regression-guard suite
(`api-axios.test.ts`, from `auth-token-auto-refresh`) spies on `axios.post` specifically, and
a `fetch` call is invisible to it — an unavoidable contract conflict discovered by T-02-03's
implementer, who correctly refused to force a false "tests pass" tick. Corrected: the module
now uses `axios.post` instead of `fetch` (axios was already a pos-web dependency via
`api-axios.ts`). Fully transparent to `http.ts`/`api-axios.ts`, which only call `refreshOnce()`
and never see its internal transport. ADR-03 (`03-logical-design.md`) is unaffected — it
governs the two *clients'* own transports, not what this shared helper uses internally.
