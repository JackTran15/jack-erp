# T-03-03 — PosRequireAuth attempts a silent refresh on every navigation

## Context
Added after reopening ADR-02 (see `03-logical-design.md` ADR-04) — a live G4 demo found that
T-03-01's fix only covers "the POS app loads" (mount-time, `PosSessionHandoff`), not "the
user navigates" (client-side route change while the tab has stayed open, e.g. all-day POS
terminal usage). `PosRequireAuth` re-evaluates `authService.isAuthenticated()` on every
navigation via `useLocation()` and, until this ticket, redirected immediately on `false` with
no chance to refresh.

Reproduction that found this: clear `pos_access_token` from `localStorage` (leave
`pos_refresh_token` valid), then click a nav link *without reloading the page* — hard
redirect to `/dang-nhap`, no `POST /auth/refresh` in the network tab.

## Implementation notes
`PosRequireAuth` needs to become stateful, but must not introduce a flicker on the common
(token-still-valid) path, and must not redirect prematurely on the transitional render where
the token has *just* gone invalid but a restore hasn't been attempted yet (React effects run
after paint — a naive `useEffect` will still let one render slip through with stale state).

Traced-through, verified-correct shape:

```tsx
import { useEffect, useState } from "react";
import { Navigate, Outlet, useLocation } from "react-router-dom";
import { authService } from "@erp/pos/services/auth.service";
import { restoreSessionIfNeeded } from "@erp/pos/components/common/PosSessionHandoff/PosSessionHandoff";

type RestoreState = "idle" | "pending" | "failed";

export function PosRequireAuth() {
  const location = useLocation();
  const authenticated = authService.isAuthenticated(); // fresh every render, never stale
  const [restoreState, setRestoreState] = useState<RestoreState>("idle");

  useEffect(() => {
    if (authenticated) {
      setRestoreState("idle"); // reset so the next expiry gets its own attempt
      return;
    }
    if (restoreState !== "idle") return; // already pending/failed for this falsy streak
    setRestoreState("pending");
    let cancelled = false;
    restoreSessionIfNeeded().finally(() => {
      if (cancelled) return;
      setRestoreState(authService.isAuthenticated() ? "idle" : "failed");
    });
    return () => { cancelled = true; };
  }, [authenticated, restoreState]);

  if (authenticated) return <Outlet />;
  if (restoreState === "failed") {
    const from = `${location.pathname}${location.search}${location.hash}`;
    return <Navigate to="/dang-nhap" replace state={{ from }} />;
  }
  return null; // idle-about-to-restore, or pending — never Outlet, never Navigate here
}
```

Why this shape specifically:
- `authenticated` is computed directly in the render body (not stored in state), so the
  common case — token valid — renders `<Outlet />` synchronously on every render, zero
  flicker, zero extra async work.
- The falsy branch never renders `<Outlet>` or `<Navigate>` until `restoreState` has
  actually resolved to `"failed"` — the transitional render (token just went invalid) renders
  `null`, not a premature redirect.
- `restoreSessionIfNeeded` (exported by `PosSessionHandoff.tsx`, from T-03-01) is reused
  as-is — it already no-ops correctly when already-authenticated or when no refresh token
  exists, and delegates to the shared single-flight `refreshOnce()` (UOW-02), so redundant
  calls from this component and `PosSessionHandoff`'s own mount-time check collapse into one
  network request when they overlap.

Do not import from a barrel/index — this repo forbids `index.ts` re-exports; import
`restoreSessionIfNeeded` directly from `PosSessionHandoff.tsx`'s file path.

## Verification note
Live verification initially hit a false signal: the refreshed token decoded to `exp - iat
= 900` (the pre-fix default), which looked like UOW-01 hadn't taken effect. Root cause:
port 4000 was being served by a **different checkout** (`erp2/apps/api/dist/main`, a
sibling project directory, started independently of this session), not this repo's API --
this session's own `dev-api` had silently died earlier (backgrounded via plain `nohup ... &`
instead of the harness's tracked `run_in_background`, which does not survive). The
navigation/redirect behavior under test here is frontend-only and unaffected by which
backend answered, so that part of the verification stood. The TTL claim was re-verified
cleanly and unambiguously via a direct `curl` login against this repo's own API restarted
on port 4001 (bypassing the frontend and the contaminated port entirely):
`"expiresIn":86400`, decoded access token `exp - iat = 86400`, refresh token
`exp - iat = 2592000` -- both exact.

## Post-review correction
First code-review pass: **BLOCKED**. The reviewer found a real bug the live verification
above missed: `restoreState` was both written by the effect and listed in the effect's own
dependency array, so `setRestoreState("pending")` caused React to re-run the effect (and
cancel it, via the `cancelled` closure) *before* a real `/auth/refresh` network round-trip
resolved — every genuine refresh got permanently stuck at `"pending"`, freezing the entire
authenticated route subtree on a blank screen with no self-recovery. The live click-through
above happened not to catch this because the manual re-navigate/reload step used to inspect
the destination page masked it — the state machine never actually recovered on its own; it
was reset by the reload. The reviewer confirmed the bug with an isolated React 19 + jsdom
repro before reporting it.

Fixed per the reviewer's suggested shape: the in-flight guard now lives in a `useRef`
(`inFlightRef`), not in `restoreState`, so the effect's dependency array is just
`[authenticated]` and writing `restoreState` inside the effect no longer re-triggers it.
Also swapped the pending branch's `return null` for a visible "Đang khôi phục phiên…"
message (matching `PosSessionHandoff`'s own treatment and `backoffice-web`'s
`RequireAuth.tsx`), per the reviewer's second note — a silent `null` made a stuck state
visually indistinguishable from a working brief pending state.

**Second code-review pass: BLOCKED again.** The fix above closed the original hole but
opened an identical one: this app runs in `<StrictMode>` (`main.tsx`), and React's
documented dev-only setup→cleanup→setup double-invoke on a component's *first mount* hit
the same effect. If `authenticated` was already `false` at first mount (e.g. a fresh tab
with no refresh token at all — exactly the "Done when" item 3 scenario), invocation A's
cleanup fired synchronously (`cancelled = true`) without releasing `inFlightRef`; the
surviving invocation B then saw `inFlightRef.current` still `true` and bailed with no
cleanup of its own, so when invocation A's `.finally()` later ran, `cancelled` was already
true and `restoreState` never left `"pending"` — the same permanent freeze, now triggered on
mount instead of on re-render. Reviewer confirmed with a hand-built harness replaying React's
documented StrictMode contract against the actual effect body (no jsdom/`@testing-library/
react` installed in this repo).

Fixed by also releasing `inFlightRef.current = false` in the cleanup, not just in
`.finally()` — safe against duplicate network calls since `refreshOnce()` is already
single-flight, so a second attempt the reset permits only ever collapses into the same
in-flight request. Re-verified live, targeting exactly the scenario the second review
flagged: cleared both tokens, did a **full page reload** (not a client-side nav) so
`PosRequireAuth` mounts fresh with `authenticated=false` from its very first render — the
exact StrictMode-double-invoke-on-mount path. Result: clean redirect to `/dang-nhap`, no
freeze. Re-verified the successful-restore path once more too (expired access token, valid
refresh token, client-side nav after login) — still self-recovers with no reload, as before.
`pnpm --filter @erp/pos-web build` clean; full `vitest run` unchanged from the established
baseline (15 passed / 1 failed file, the pre-existing unrelated `api-axios.test.ts` issue).

Re-verified live, twice, specifically watching for the destination route to actually paint
*without* any reload: cleared `pos_access_token`, clicked a nav link, confirmed the target
page rendered real content (not blank) and a fresh access token was present, with no manual
reload in between. Repeated a second time from a different starting route. Both self-recovered.
`pnpm --filter @erp/pos-web build` clean; full `vitest run` shows the same pre-existing
15-passed/1-failed file baseline as before this ticket (the unrelated `api-axios.test.ts`
spy issue) — no new regression.
