# T-01-01 — Project `pointsBalanceAfter` from the gated value

## Context

`PersistInvoiceStep.execute` writes two point figures back to back. Line 73 gates the earn:

```ts
invoice.pointsEarned = invoice.customerId && !totals.pointsBlocked ? totals.pointsEarned : 0;
```

Line 86, inside the `pointsBalanceAfter` projection, then ignores it and re-reads the raw
total:

```ts
cardBalance - Number(invoice.pointsRedeemed ?? 0) + totals.pointsEarned,
```

For a blocked invoice that is `7575 - 0 + 80 = 7655` — the number QA saw on the receipt for a
card holding 7.575. `pointsBlocked` is the second of the two gate conditions and was never
propagated here; the comment on lines 68-72 asserting the projection "has always been guarded
this way" is true only of the `customerId` half.

ADR-03 states the rule this ticket applies: `points_balance_after` is projected from the
persisted columns on the same row, never from `totals.*`.

## Implementation notes

- Change `totals.pointsEarned` to `invoice.pointsEarned` in the `Math.max(0, …)` expression.
  That is the entire behavioural change — `invoice.pointsEarned` is assigned on line 73,
  before this statement, so no reordering is needed.
- Fix the comment on lines 68-72: it currently claims the projection below has always been
  guarded. Say instead that the projection reads `invoice.pointsEarned` precisely so the
  `customerId` **and** `pointsBlocked` gates apply to both numbers, and reference ADR-03.
- Do not extract a shared helper for the three projection sites. ADR-03 is explicit that the
  coupling should stay visible at each site; a helper would hide it.
- Do not touch `checkout-invoice.service.ts` (A-08) or anything on the earn side.
- No migration (A-07): `points_balance_after` already exists on `invoice.entity.ts:98`.
