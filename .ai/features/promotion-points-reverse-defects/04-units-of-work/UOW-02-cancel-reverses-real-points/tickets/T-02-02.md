# T-02-02 — Cancel sends `points: invoice.pointsEarned`

## Context

`CancelInvoiceService.cancel` gets the invoice's own numbers right and then throws them away
when it publishes. Line 96 sets `invoice.pointsReversed = invoice.pointsEarned` (0 for a
blocked invoice) and line 116 projects `pointsBalanceAfter` from that — both correct. Line
168 then publishes:

```ts
subtotalDelta: Number(invoice.amountDue),
```

and the consumer turns 800.000đ into 80 points and debits a card that never earned them. The
snapshot says 0, the card says −80, and the customer's history shows a row the invoice denies.

A cancel voids the whole sale, so the ratio is 1 and no proration is involved — the number to
reverse is exactly `invoice.pointsEarned`. For accruing invoices this changes nothing, because
both sides compute `floor(amountDue / POINT_EARN_VND_PER_POINT)` (A-03, verified at
`compute-totals.step.ts:83` and the `invoice.entity.ts:85` column comment).

## Implementation notes

- Add `points: Number(invoice.pointsEarned ?? 0)` to the
  `loyaltyPointsReversePublisher.publish` call. Keep `subtotalDelta: Number(invoice.amountDue)`
  — it stays as the audit value and keeps the publisher's existing guard working, so a blocked
  cancel still publishes and still writes the replay marker.
- The invoice is read before the transaction and `pointsEarned` is not mutated by the cancel,
  so no re-read is needed. Read it off the same `invoice` object the surrounding code uses,
  not off `cancelledInvoice`.
- Comment the line the way the neighbouring code is commented: say why the recorded count
  beats the amount due, naming the blocked-accrual case, so the next person to touch this does
  not "simplify" it back to money.
- Nothing else in this service changes. Lines 96 and 116 were already right — that they were
  right while the card was wrong is the symptom, not a second bug.
