# T-02-03 — Spec for the three cancel cases

## Context

`cancel-invoice.service.spec.ts` asserts the publish payload today
(`expect.objectContaining({ subtotalDelta: 200 })`, line ~347) and the balance projection
(line ~387, ~422, ~433). Every existing case has a nonzero `pointsEarned`, so nothing pins
what happens when the invoice earned nothing while money still moved — which is precisely
defect #16.

## Implementation notes

- **AC-04, the reported case.** Invoice with `pointsEarned: 0`, `amountDue: 800000`,
  `customerId` set. Assert the publish payload contains `points: 0` — and assert
  `subtotalDelta` is still `800000`, so a future "simplification" that drops the money value
  and breaks the publisher guard fails here.
- **AC-05, the regression.** Invoice with `pointsEarned: 80`, `amountDue: 800000` → payload
  carries `points: 80`. This is the case that proves A-03: the number did not change.
- **AC-06, redeem side.** Invoice with `pointsEarned: 0` and `pointsRedeemed: 100` on a
  blocked promotion → `refundRedeemedPoints` is called with 100, the payload carries
  `points: 0`, and `pointsBalanceAfter` equals `cardBalance + 100`.
- Assert on the publisher mock's argument, not on card state: the card mutation happens in the
  consumer, which T-02-01 already covers. Testing it again here would need the consumer wired
  into this spec and would prove nothing new.
- Do not modify the existing cases. `subtotalDelta: 200` and the `4165` / `null` / `0` balance
  expectations are the no-change contract for accruing cancels.
