# T-03-02 — Spec for the capped return reverse, plus the full-suite regression

## Context

`checkout-return.service.spec.ts` is the densest of the three specs this feature touches and
the one most exposed to an accidental behaviour change. It pins `subtotalDelta` at 190
(line ~938), 500 (~990), 800 (~1315) and 464.000 (~1538), the derived-points relation
`floor(subtotalDelta / POINT_EARN_VND_PER_POINT)` (~1536), and `pointsBalanceAfter` at 161 /
0 / null / 5.002 (~1056, ~1067, ~1078, ~1741, ~1755). ADR-02's cap is a no-op on all of them;
this ticket's job is to prove that rather than assume it, and then add the case that was
missing.

## Implementation notes

- **AC-07.** Original invoice with `pointsEarned: 0` and `amountDue: 800000`, every line
  returned. Assert the return document's `points_reversed = 0` **and** that the published
  payload carries `points: 0` with `subtotalDelta` still positive. Both, in one case — one
  disagreeing with the other is the whole defect.
- **AC-08, full.** Original with `pointsEarned: 80`, full return → `points: 80` and
  `points_reversed = 80`, i.e. the cap binds exactly and changes nothing.
- **AC-08, partial.** Original with `pointsEarned: 80`, returned lines netting 464.000 →
  `points: 46`, below the cap, identical to today. This is the case A-02 was chosen to
  protect.
- **AC-09.** QUICK return with `originalInvoice = null` → uncapped derivation, unchanged.
- Add a case where the cap would bind on a partial return of a *blocked* original — returned
  lines netting 464.000 against `pointsEarned: 0` → `points: 0`. Without it, a `min` written
  as a `max` would still pass every other case.
- The full-suite run matters here specifically: this service is called from the return, the
  exchange and the quick-exchange flows, and the reverse publisher is shared with cancel.
