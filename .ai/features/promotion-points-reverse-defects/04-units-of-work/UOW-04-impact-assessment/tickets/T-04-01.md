# T-04-01 — The assessment queries

## Context

`apps/api/scripts/` is where this repo keeps one-off operational scripts
(`sync-goods-receipt-permissions.sql`, `revert-double-cancelled-receipt-fix.py`,
`verify-temp-warehouse-remaining.mjs`). This one joins that set. It runs against
`erp_clone_prod` on localhost:5433 — a real clone of production, so read-only is not a style
preference here (A-06, and the project's standing rule about that database).

Two footprints to measure:

- **#15** — `invoices.points_balance_after` written with an earn the invoice did not record.
- **#16** — `point_history` rows with `delta < 0` against an invoice whose
  `points_earned = 0`, i.e. points clawed back that were never accrued.

## Implementation notes

- Three `SELECT`s, each with a comment naming the defect it measures. No CTE gymnastics —
  someone reading this in six months should be able to check the predicate by eye.
- **#16 first**, because it is the exact and unarguable one: join `point_history` to
  `invoices` on `invoice_id`, filter `delta < 0 AND invoices.points_earned = 0`. Report the row
  count, the summed magnitude of `delta`, and a per-organization breakdown. There is no
  legitimate reason for such a row to exist.
- **#15** needs a narrow predicate, because redemption, reversal and later returns all move the
  balance legitimately. Restrict to `points_earned = 0 AND points_balance_after IS NOT NULL`
  and compare against what the row's own columns imply. State the predicate in a comment and
  say plainly what it does not catch — a partial measure that is honest about its edges beats a
  broad one nobody trusts.
- Third query: the dev/real split. Group by `organization_id` joined to the organization name
  so the write-up can say which rows are demo data.
- Include the clone's snapshot date in the output — a `SELECT max(created_at) FROM invoices` is
  enough to date the numbers.
- Header comment: what the script is for, which database it is meant for, and that it writes
  nothing.
