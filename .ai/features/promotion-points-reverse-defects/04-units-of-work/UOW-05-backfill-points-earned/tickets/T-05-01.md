# T-05-01 — Backfill migration

## Context

`invoices.points_earned` was added by `c9488fab` on 2026-07-16. Rows written around that
deploy never had it populated: on `erp_clone_prod`, 24 of 90 posted customer sales read 0
while `point_history` shows a real earn, 3.224 points in total, the newest issued 2026-07-19.
ADR-02's cap reads this column and treats 0 as "earned nothing", so until it is repaired the
cap would refuse to reverse those points.

ADR-05 chose a migration over an ops script purely for ordering: the cap must not reach an
environment the repair has not. Note this is the repo's first data-writing migration — every
existing one is schema-only.

## Implementation notes

- Generate the file with the repo's convention (`pnpm migration:generate` names it, or follow
  the existing timestamp naming by hand — do not invent a different scheme).
- `up()`: a single `UPDATE ... FROM` against a grouped subquery over `point_history`, e.g.
  update `invoices` set `points_earned` = the summed `delta` of that invoice's `earn` rows,
  where `points_earned = 0` and that sum is `> 0`. Derive rows by predicate — never a
  hard-coded id list, because production may hold more than the clone's 24.
- Only `type = 'earn'` rows. The enum is stored **lowercase** (`earn` / `redeem` / `adjust`);
  `'EARN'` raises `invalid input value for enum point_type_enum`.
- Restrict to what the ledger positively supports: `points_earned = 0 AND sum > 0`. That
  leaves the three A-12 rows — column right, ledger empty — untouched, which is required by
  AC-14.
- Log the affected count before and after the update, so the demo's step 2/3 comparison is
  possible and the real production number ends up in the deploy log.
- `down()`: set `points_earned = 0` for the same predicate set. Exact, because every row this
  touches was 0 beforehand. Capture the ids in `up()` if that is what it takes to make
  `down()` precise rather than approximate.
- Do not touch `points_reversed` (Finding A) or credit any card (Finding C). Both are out of
  scope for this UoW and each needs a different kind of correction.

## Construction note

Rehearsed on `erp_clone_prod` by executing this migration's exact statements rather than
`pnpm migration:run`: the clone sits at timestamp 1788000000000 with 143 migrations applied,
so `migration:run` would have applied **15** pending migrations there, not one. Applying 14
unrelated schema changes to a production clone is a different action from rehearsing this
backfill, and was not what was authorised. `migration:run` on an up-to-date environment is
still the intended delivery mechanism (ADR-05) and remains untested end to end.
