# T-05-02 — Prove the repair, and leave the assessment true

## Context

`08-impact-assessment.md` records Finding B as an open problem — 24 rows, 3.224 points. Once
T-05-01 runs, that is history rather than a live finding, and an assessment that still reads
as current would send the next person hunting for rows that are no longer there.

The assessment script has no query for Finding B; the numbers were produced ad hoc while
implementing T-03-01. Folding it in means the check is repeatable on any environment, which
matters because production's count is not the clone's.

## Implementation notes

- Add a section 4 to `assess-points-reverse-damage.sql`: invoices where `points_earned`
  disagrees with the summed ledger earn, split by direction (column empty vs ledger empty), so
  both Finding B and Finding C are visible from the script rather than from prose.
- Keep it read-only, and keep every `\echo` free of apostrophes — an unbalanced quote in a
  psql meta-command silently swallows the statements after it, which is how five queries went
  missing on the first run of this file.
- Verify with `psql -v ON_ERROR_STOP=1` and assert the new headers appear in the output.
  Grepping for `ERROR` is not sufficient and was the check that failed to catch this before.
- Update `08-impact-assessment.md`: Finding B becomes resolved, with before-and-after numbers
  and the migration that did it. Finding A and Finding C stay open.

## Done when

- [x] Section 4 exists in the script and reports both directions of disagreement
- [x] The script runs under `ON_ERROR_STOP=1` with exit 0, and every result-set header is
      asserted present in the output — not merely an absence of `ERROR`
- [x] Post-migration, section 4 reports 0 rows in the column-empty direction and 3 in the other
- [x] `08-impact-assessment.md` marks Finding B resolved with before/after numbers, and leaves
