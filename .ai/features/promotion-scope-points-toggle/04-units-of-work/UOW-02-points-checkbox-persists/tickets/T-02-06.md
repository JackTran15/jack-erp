# T-02-06 — Tests: `accruePoints` round-trips end to end

## Context

Four independent hops carry this field (entity ↔ domain, domain ↔ application DTO, FE
mapper ↔ application DTO). A round-trip test at each boundary is cheaper and more precise
than one big integration test, and matches how `invoiceScope` is already tested at each of
these files.

## Implementation notes

- `promotion-program.spec.ts` (backend, domain): `PromotionProgram.create({ ...validProps,
  accruePoints: true })` exposes `.accruePoints === true`; a props object omitting it (if the
  type allows, otherwise skip) is not required since the field is non-optional — cover both
  `true` and `false` construction instead.
- `promotion.mapper.ts` spec (backend, application/mappers): `toDomain()` given a row with
  `program.accruePoints = true` produces an aggregate with `accruePoints === true`;
  `toPersistence()` given an aggregate with `accruePoints = false` produces an entity with
  `accruePoints === false`. Round-trip both directions, both values.
- `promotion.mapper.ts` spec (FE, api/): `invoiceDiscountToDto()` given `form.accruePoints =
  true` emits `{ accruePoints: true, ... }`; `invoiceDiscountFromDetail()` given
  `detail.accruePoints = true` sets `base.accruePoints = true`, and given `detail.accruePoints
  = undefined` (an old row read before this migration ran, in case a stale cached response
  ever reaches the FE) defaults to `false` rather than crashing or leaving it `undefined`.
- Run backend via `pnpm --filter @erp/api test -- promotion-program.spec.ts promotion.mapper.spec.ts`;
  run FE via `npx vitest run apps/backoffice-web/src/pages/promotions/api/promotion.mapper.spec.ts`
  (same convention as T-01-03).
