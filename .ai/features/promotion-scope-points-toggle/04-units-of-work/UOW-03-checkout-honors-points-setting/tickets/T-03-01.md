# T-03-01 — Surface `accruePoints` on `AppliedProgram`, guarded to INVOICE_DISCOUNT

## Context

`ctx.promotion.appliedPrograms` (populated by `evaluate-promotion.step.ts`, which does a
structural passthrough of `evaluation.appliedPrograms` — no change needed there) is the only
place `compute-totals.step.ts` (T-03-02) can learn whether a given applied program allows
points. That value has to be attached to `AppliedProgram` by `toAppliedProgram()`
(`promotion-resolver.ts:179-198`), the single site that builds this shape from the domain
`PromotionProgram` aggregate (T-02-03 gives it `.accruePoints`).

**This is the one correctness-critical detail in the whole feature (see
`03-logical-design.md`'s Domain model + Alternatives rejected sections).**
`accrue_points` defaults to `false` on every program row regardless of type. If
`accruePoints` were populated unconditionally on `AppliedProgram`, every checkout that
applies a product-discount / tiered-discount / buy-get / gift program would start blocking
points, because those types have no UI to ever set the column to `true` (A-05). The existing
`discountMode`/`discountValue` conditional spread in `toAppliedProgram()` (only set when
`type === PromotionProgramType.INVOICE_DISCOUNT`) is the pattern that prevents this — extend
that exact same conditional, do not add a second one.

## Implementation notes

`evaluation.ts` (domain-internal `AppliedProgram`, line 20-37) and
`packages/shared-interfaces/src/promotion/index.ts` (wire-facing `AppliedProgram`, line
237-254) both get:

```ts
/**
 * Only set when `type === INVOICE_DISCOUNT` — mirrors discountMode/discountValue above.
 * Undefined (never `false`) on the other 4 types, so a checkout that applies one of them
 * can never have its points blocked by this field's absence of meaning for that type.
 */
accruePoints?: boolean;
```

`promotion-resolver.ts`'s `toAppliedProgram()` (line 179-198): extend the existing
conditional spread —

```ts
...(program.type === PromotionProgramType.INVOICE_DISCOUNT
  ? { discountMode: program.discountMode, discountValue: program.discountValue, accruePoints: program.accruePoints }
  : {}),
```

Do not add a separate `if`/spread — reusing the same conditional keeps the "which fields are
INVOICE_DISCOUNT-only" list in one place.

`evaluate-cart.handler.ts`'s `toEvaluateResponse()` needs no change — it already does
`appliedPrograms: evaluation.appliedPrograms` as a structural passthrough.

## Done when

- [x] `AppliedProgram.accruePoints` exists on both type declarations
- [x] An applied `INVOICE_DISCOUNT` program with `accruePoints: true` on the aggregate
      produces `AppliedProgram.accruePoints === true`
- [x] An applied `ITEM_DISCOUNT` / `TIERED_DISCOUNT` / `BUY_M_GET_N` / `GIFT_ITEM` program
      produces `AppliedProgram.accruePoints === undefined`, never `false`, regardless of
      what the underlying row's `accrue_points` column holds
- [x] `pnpm --filter @erp/api build` compiles clean

Verified with real tests in `promotion-resolver.spec.ts` (`describe('accruePoints on
AppliedProgram (INVOICE_DISCOUNT only)')`, 6 cases): true/false pass through for
INVOICE_DISCOUNT, and an `it.each` over the other 4 types each constructs the program with
`accruePoints: true` on the aggregate and asserts `AppliedProgram.accruePoints` is
`undefined` — proving the conditional-spread guard, not just inspecting it. Full suite:
`pnpm --filter @erp/api test -- promotion-resolver.spec.ts` → 35/35 passed.
