# T-03-02 — `compute-totals.step.ts` derives `pointsBlocked`

## Context

Per ADR-02, the "does this invoice earn points" decision is made exactly once, here, and
threaded through the saga context — never re-derived by any later step or consumer.

## Implementation notes

`checkout-step.ts`'s `CheckoutTotals` interface (line 113-133): add
`pointsBlocked: boolean;` next to `pointsEarned: number;` (line 131).

`compute-totals.step.ts`: after computing `pointsEarned` (line 83), derive:

```ts
const appliedPrograms = (ctx.promotion?.appliedPrograms ?? []) as AppliedProgram[];
const pointsBlocked = appliedPrograms.some((p) => p.accruePoints === false);
```

Import `AppliedProgram` from `@erp/shared-interfaces` (same import `persist-invoice.step.ts`
already uses for the same cast). Note this check does **not** need to filter by
`type === INVOICE_DISCOUNT` — T-03-01 already guarantees `accruePoints` is `undefined`
(never `false`) on every non-invoice-discount applied program, so `.some(p => p.accruePoints
=== false)` is naturally correct without an extra type check. Do not add one; it would be
redundant with T-03-01's guarantee and would obscure that the guarantee is what makes this
line safe.

Add `pointsBlocked` to the `ctx.totals = { ... }` object literal (line 143-155), next to
`pointsEarned`.

## Done when

- [x] `ctx.totals.pointsBlocked` is `true` when any applied program has `accruePoints ===
      false`
- [x] `ctx.totals.pointsBlocked` is `false` when all applied programs have `accruePoints ===
      true`, or none are `INVOICE_DISCOUNT`, or no programs are applied at all
- [x] `pnpm --filter @erp/api build` compiles clean

Dedicated assertions for these scenarios are T-03-04's job (`preflight-steps.spec.ts`, per the
ticket graph) — not duplicated here. This ticket's own verification: full build clean, plus
the entire `checkout-saga` suite (23 files / 277 tests) still green after adding the required
`pointsBlocked: false` field to 4 other spec files' `totals` fixtures that the new required
`CheckoutTotals.pointsBlocked` field broke compilation for (orphan cleanup, same reasoning as
T-02-03/T-02-04): `create-debt.step.spec.ts`, `post-journal.step.spec.ts`,
`enqueue-outbox.step.spec.ts`, `persist-invoice.step.spec.ts`.
