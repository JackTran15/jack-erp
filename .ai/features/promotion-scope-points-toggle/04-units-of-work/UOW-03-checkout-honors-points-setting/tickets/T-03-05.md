# T-03-05 — Async-path tests: `pointsBlocked` → outbox enqueue/skip

## Context

Covers the "no drift" half of AC-07/AC-09/AC-11 and the regression half of AC-08/AC-10, at
the outbox-row level — this is deliberately not a full Kafka-consumer integration test:
`loyalty-points.consumer.ts` and `membership-card.service.ts` are untouched by this feature
(ADR-02), so asserting the outbox row is/isn't written is sufficient proof that the
consumer will/won't fire (`awardPointsForInvoice` has exactly one caller, verified during
design — no other trigger path exists).

## Implementation notes

In `enqueue-outbox.step.spec.ts`, add cases for:
- `ctx.totals.pointsBlocked = true`, `invoice.customerId` set → no `LOYALTY_POINTS_AWARD`
  row is enqueued (assert on whatever mock/spy this spec already uses for
  `OutboxService.enqueue` — filter calls by `ERP_TOPICS.LOYALTY_POINTS_AWARD`) (AC-07,
  AC-09).
- `ctx.totals.pointsBlocked = false`, `invoice.customerId` set → the row **is** enqueued,
  with `payload.subtotal === totals.amountDue`, unchanged from current behavior (AC-08,
  AC-10, AC-11).
- Confirm the other three outbox rows (`SALE_POSTED`, `TEMP_WAREHOUSE_INVOICE_FULFILL`, and
  `CASH_VOUCHER_NEEDED_KEPT_CHANGE` when applicable) are enqueued identically regardless of
  `pointsBlocked` — this feature must not have any effect on them.

## Done when

- [x] No `LOYALTY_POINTS_AWARD` outbox row when `pointsBlocked === true`
- [x] `LOYALTY_POINTS_AWARD` outbox row enqueued, unchanged payload shape, when
      `pointsBlocked === false`
- [x] The other 3 outbox event types are unaffected by `pointsBlocked` in either case
- [x] `pnpm --filter @erp/api test -- enqueue-outbox.step.spec.ts` is green

Real output: `Test Suites: 1 passed, 1 total / Tests: 15 passed, 15 total`. The
`erp.loyalty.points.award` topic is asserted absent/present via `enqueue.mock.calls` topic
filtering (not just a zero-valued field) — the actual outbox-skip assertion UOW-03's
Definition of Done calls for. A third case also proves the kept-change voucher row (the one
`CASH_VOUCHER_NEEDED_KEPT_CHANGE`-adjacent event that can co-occur) still fires normally when
`pointsBlocked === true`, showing the two are independent.
