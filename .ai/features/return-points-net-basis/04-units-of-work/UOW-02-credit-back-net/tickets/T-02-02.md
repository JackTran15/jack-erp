# T-02-02 — computeRedeemedCreditBack theo tỷ lệ returnedNet/amountDue

## Context

Theo ADR-01, mẫu số đúng là `originalInvoice.amountDue`, vì
`Σ netLine − headerResidual = amountDue`. Chọn `Σ netLine` làm mẫu số là phương án đã bị loại
ở `03-logical-design.md`: nó bỏ sót `headerResidual` nên trả toàn bộ hoá đơn sẽ **không** hoàn
đủ số điểm khách đã tiêu — mà đó đúng là đầu mút AC-07 kiểm.

Trường hợp biên không phải giả thiết: `INV-202608-00010` đang nằm trong DB dev với
`amount_due = 0` (subtotal 750.000, khuyến mại 150.000, điểm 600.000) vì khách trả trọn bằng
điểm. Mẫu số bằng 0 ở đúng hoá đơn đó (A-07).

## Implementation notes

- Cổng vào giữ nguyên tinh thần cũ, bỏ điều kiện `originalSubtotal <= 0` khỏi cổng chính vì
  mẫu số đã đổi:
  ```ts
  if (!originalInvoice ||
      Number(originalInvoice.pointsRedeemed) <= 0 ||
      totals.returnSubtotal <= 0) {
    return 0;
  }
  const amountDue = Number(originalInvoice.amountDue);
  if (amountDue <= 0) {
    // Settled entirely with points — no money basis left to prorate against.
    const originalSubtotal = Number(originalInvoice.subtotal ?? 0);
    if (originalSubtotal <= 0) return 0;
    return Math.floor(
      (Number(originalInvoice.pointsRedeemed) * totals.returnSubtotal) / originalSubtotal,
    );
  }
  return Math.floor(
    (Number(originalInvoice.pointsRedeemed) * totals.returnedNet) / amountDue,
  );
  ```
- Giữ `Math.floor` — đó là cái chặn không cho nhiều lần trả từng phần hoàn quá số đã tiêu
  (AC-09), và docblock hiện có đã nói đúng ý này, giữ lại câu đó.
- Cập nhật docblock của hàm bằng tiếng Anh: nêu mẫu số mới, nêu vì sao `amountDue` chứ không
  phải `Σ netLine`, nêu nhánh `amountDue <= 0` tồn tại vì hoá đơn trả trọn bằng điểm.
- **Không** đụng `computeReverseBase` trong ticket này — đó là T-01-02.
