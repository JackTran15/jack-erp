# T-02-01 — Add formatViDate / formatViDateTime to packages/ui

## Context

Per confirmed assumption A-02 and ADR-02 in `03-logical-design.md`, the shared FE
formatter lives in `packages/ui`, following the existing precedent
`packages/ui/src/lib/money-format.ts` (a pure formatting helper, re-exported from
`packages/ui/src/index.ts` as `formatMoneyInteger` / `formatVnd`). This ticket only adds
the new file and its exports — it does not touch any call site (T-02-02..T-03-01 do that).

## Implementation notes

- New file `packages/ui/src/lib/date-time-format.ts`:
  ```ts
  export interface FormatViDateTimeOptions {
    withSeconds?: boolean; // default: false
  }

  export function formatViDateTime(
    input: Date | string,
    options: FormatViDateTimeOptions = {},
  ): string {
    const d = input instanceof Date ? input : new Date(input);
    if (Number.isNaN(d.getTime())) return "";
    return new Intl.DateTimeFormat("vi-VN", {
      day: "2-digit",
      month: "2-digit",
      year: "numeric",
      hour: "2-digit",
      minute: "2-digit",
      ...(options.withSeconds ? { second: "2-digit" } : {}),
      hour12: false,
      timeZone: "Asia/Ho_Chi_Minh",
    }).format(d);
  }

  export function formatViDate(input: Date | string): string {
    const d = input instanceof Date ? input : new Date(input);
    if (Number.isNaN(d.getTime())) return "";
    return new Intl.DateTimeFormat("vi-VN", {
      day: "2-digit",
      month: "2-digit",
      year: "numeric",
      timeZone: "Asia/Ho_Chi_Minh",
    }).format(d);
  }
  ```
  (Exact formatting-option choices — e.g. `hour12`, digit padding — should match what the
  majority of existing call sites already produce, since the goal is "same visible output,
  now zone-correct," not a redesign; the pseudocode above mirrors
  `apps/pos-web/src/lib/common/dateTime.ts`'s existing `viDateTimeFormatter` options.)
- Both functions return `""` for `null`/`undefined`-derived `NaN` dates — do not throw.
  This matches the existing fallback behaviour already present at every call site being
  migrated (see `03-logical-design.md` Contracts).
- Re-export both from `packages/ui/src/index.ts`, placed next to the existing
  `formatMoneyInteger` / `formatVnd` exports:
  ```ts
  export { formatViDate, formatViDateTime, type FormatViDateTimeOptions } from "./lib/date-time-format";
  ```
- Do not add a `timeZone` parameter to the public signature — per the Contracts section in
  `03-logical-design.md`, the zone is fixed, not configurable.

## Done when

- [x] `formatViDate` and `formatViDateTime` are exported from `packages/ui/src/index.ts`
- [x] Both always pass `timeZone: "Asia/Ho_Chi_Minh"` to the underlying
      `Intl.DateTimeFormat` call — no code path constructs a formatter without it
- [x] Both return `""` for invalid/unparseable input rather than throwing
- [x] `pnpm --filter @erp/ui build` (or the workspace-wide `pnpm build:shared`) succeeds
      — DEVIATION: `@erp/ui` has no `build` script (`main: ./src/index.ts`, source-only,
      confirmed in `package.json` — no build step exists to run). Verified instead with
      `npx tsc --noEmit -p tsconfig.json` (zero errors in `date-time-format.ts`) and
      `npx vitest run date-time-format.test.ts` (3/3 passing, T-02-05). Real consumption
      is verified when backoffice-web (T-02-02..04) and pos-web (T-03-01) build against
      the new exports.
- [x] DEVIATION (found during implementation, not in ticket): `formatViDateTime`'s body
      does not use `Intl.DateTimeFormat(...).format(d)` directly as the ticket's
      pseudocode showed — `vi-VN`'s combined date+time CLDR pattern for these fields
      renders time-first (`"07:00 01/01/2026"`), confirmed independent of `timeZone`,
      contradicting the `dd/MM/yyyy HH:mm` output contract in `03-logical-design.md`
      Contracts. Rewritten to build the string from `formatToParts` (matching the pattern
      pos-web's own `dateTime.ts` already uses for its default case, for the same reason)
      so the documented output order is guaranteed.
