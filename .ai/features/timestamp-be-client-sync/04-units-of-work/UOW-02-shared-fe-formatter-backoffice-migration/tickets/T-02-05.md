# T-02-05 — Unit test proving the shared formatter is timezone-independent

## Context

AC-09 requires a test harness that forces a non-Vietnam TZ and asserts the shared
formatter still renders the correct Asia/Ho_Chi_Minh wall-clock value. `packages/ui` has
no existing test files or vitest config; `apps/pos-web` and `apps/backoffice-web` already
run `.test.ts` files via `npx vitest run` despite `package.json`'s `"test": "echo test"`
script (vitest resolves from the workspace without a dedicated config file, defaulting to
`node` test environment — confirmed working for existing suites, e.g.
`apps/pos-web/src/lib/page-libs/checkout/checkoutSettlement.test.ts`). This is a pure-TS
formatter test with no DOM dependency, so the same mechanism applies here.

**TZ-testability decision:** use direct `process.env.TZ` mutation inside the test file,
the same mechanism as the backend's T-01-02, rather than mocking
`Intl.DateTimeFormat.prototype.resolvedOptions` or relying on a Vitest config-level `env`
override. This works reliably because:
- The repo requires Node `>=20` (`CLAUDE.md`), which ships full ICU by default — no
  `--icu-data-dir` / `--experimental-vm-modules` workaround is needed for `Intl` to
  respect a runtime-changed `TZ`.
- `formatViDate` / `formatViDateTime` always pass an explicit `timeZone` option (per
  T-02-01), so the test is not actually relying on Node's `Intl` re-reading `process.env.TZ`
  correctly — it is proving the explicit option makes `process.env.TZ` irrelevant, which is
  the actual guarantee AC-09 asks for.
- No vitest config/setup file exists to add a `TZ` override to, and none is needed for a
  single-file `process.env.TZ = '...'` mutation.

## Implementation notes

```ts
import { describe, it, expect, afterAll } from "vitest";
import { formatViDate, formatViDateTime } from "./date-time-format";

describe("formatViDateTime / formatViDate — timezone independence", () => {
  const originalTz = process.env.TZ;
  process.env.TZ = "America/New_York"; // arbitrary non-Vietnam zone

  afterAll(() => {
    process.env.TZ = originalTz;
  });

  it("formats a fixed UTC instant as Asia/Ho_Chi_Minh wall-clock time regardless of TZ", () => {
    // 2026-01-01T00:00:00Z is 2026-01-01T07:00:00+07:00 in Asia/Ho_Chi_Minh —
    // a value that would print a different calendar day under most other zones.
    const instant = new Date("2026-01-01T00:00:00Z");
    expect(formatViDateTime(instant)).toBe("01/01/2026 07:00");
    expect(formatViDate(instant)).toBe("01/01/2026");
  });

  it("returns \"\" for invalid input", () => {
    expect(formatViDateTime("not-a-date")).toBe("");
    expect(formatViDate("not-a-date")).toBe("");
  });
});
```

- Pick the exact expected output string by actually running the formatter once locally
  with `timeZone: "Asia/Ho_Chi_Minh"` and recording the result — do not hand-derive the
  UTC+7 offset by inspection alone, since `Intl.DateTimeFormat`'s exact separator/padding
  behaviour must match what T-02-01 actually implemented.
- Add a case for `withSeconds: true` if T-02-01 implemented that option.
