# T-03-01 — dateTime.ts delegates to the shared @erp/ui formatter

## Context

`apps/pos-web/src/lib/common/dateTime.ts:1-46` declares its own
`viDateTimeFormatter` / `viDateTimeWithSecondsFormatter` (no `timeZone` option) and
exports `formatViDateTime(input, { separator, withSeconds })`. This ticket makes it
delegate its actual formatting to `@erp/ui`'s `formatViDateTime` (added in T-02-01)
instead of constructing its own un-zoned `Intl.DateTimeFormat` instances — but **keeps its
own exported function name and full existing signature**, because both options it
supports have real, current callers that the shared util's signature does not cover:

- `separator: "space"` — used by
  `lib/page-libs/checkout/printing/renderInvoiceHtml.ts:393` and
  `pages/ReturnGoodsPage.tsx:47` (both need `dd/MM/yyyy HH:mm` with a space, not the
  default `" - "` dash-separator).
- `withSeconds: true` — used by
  `.../DraftInvoicesDialog/InvoiceListPanel/DraftRow/DraftRow.tsx:38`.

At least 9 other call sites (`ReturnInvoiceTable.tsx`, `InvoiceListTable.tsx`,
`PaymentSubTopBar.tsx`, `DebtTab.tsx`, `PurchaseHistoryTab.tsx`,
`InvoiceReceiptDialog.tsx`, `use-fast-stock-transfer-table-columns.tsx`, etc.) call
`formatViDateTime(value)` with no options — the default output must not change for them.

`parseViDate` (`dateTime.ts:53-68`) does no `Intl.DateTimeFormat` work — local `Date`
constructor/getter based date-only parsing — and is not touched by this ticket.

## Implementation notes

- Import `formatViDateTime as formatViDateTimeShared` (or similar) from `@erp/ui`.
- Rewrite `dateTime.ts`'s own `formatViDateTime` to call the shared util for the
  zone-correct `dd/MM/yyyy HH:mm[:ss]` string, then apply the existing
  `separator: "space"` post-processing (replacing the shared util's separator with a
  single space) exactly as `partsOf` / `part` currently do — do not change the visible
  output for any existing caller, only make the underlying `Intl.DateTimeFormat`
  construction go through `@erp/ui` (so it is TZ-safe).
- The local `viDateTimeFormatter` / `viDateTimeWithSecondsFormatter` / `partsOf` / `part`
  helpers can be deleted once `formatViDateTime`'s body no longer needs them directly —
  but only if every existing behaviour (default `" - "` separator, `"space"` separator,
  `withSeconds`) is still reproduced exactly.
- Do not touch `parseViDate` or its `FormatViDateTimeOptions` export shape (`separator`,
  `withSeconds` stay pos-web-local option names — they are not renamed to match
  `@erp/ui`'s options).
- Do not touch any of the ~11 call sites listed above — their calls to
  `formatViDateTime(...)` are unchanged; only `dateTime.ts`'s internals change.

## Done when

- [x] `dateTime.ts` no longer constructs an `Intl.DateTimeFormat` without an explicit
      `timeZone` — either directly, or by delegating entirely to `@erp/ui`'s formatter
      — now delegates 100% to `@erp/ui`'s `formatViDateTime`; no local
      `Intl.DateTimeFormat` construction remains at all.
- [x] `formatViDateTime(input)` (no options) produces byte-identical output to before this
      change, for a Vietnam-zoned input
      — verified: `"01/01/2026 - 07:00"` (dateTime.test.ts, T-03-02).
- [x] `formatViDateTime(input, { separator: "space" })` still produces a space-separated
      result (verified against `renderInvoiceHtml.ts` / `ReturnGoodsPage.tsx` usage)
      — verified: `"01/01/2026 07:00"`.
- [x] `formatViDateTime(input, { withSeconds: true })` still includes seconds (verified
      against `DraftRow.tsx` usage)

      short-circuited via `.format()` before the `separator` logic ran at all, producing
      time-first output (`"07:00:00 01/01/2026"`, confirmed empirically) that silently
      ignores whatever `separator` the caller passes — a real quirk, not documented in the
      ticket. Reproduced this exactly (time-first, single space, `separator` ignored) so
      `DraftRow.tsx`'s visible output is genuinely byte-identical, not just "still has
      seconds somewhere in the string."
- [x] `parseViDate` is unmodified — confirmed via diff, function untouched.
- [x] `pnpm --filter @erp/pos-web build` succeeds — verified (tsc + vite build, 2258
