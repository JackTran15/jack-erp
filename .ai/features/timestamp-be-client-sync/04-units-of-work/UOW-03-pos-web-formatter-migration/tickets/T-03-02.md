# T-03-02 — Test dateTime.ts under a foreign TZ + final orphaned-formatter sweep

## Context

Closes out the feature: proves pos-web's migrated `formatViDateTime` is TZ-independent
(same pattern as T-02-05, per AC-09's harness — process.env.TZ mutation, since pos-web
already runs `.test.ts` files via `npx vitest run`), and runs the final AC-07 sweep now
that both apps (UOW-02, UOW-03) are migrated.

## Implementation notes

- `dateTime.test.ts`, colocated with `dateTime.ts` (matches existing pos-web test
  colocation, e.g. `lib/page-libs/checkout/checkoutSettlement.test.ts`):
  - Force `process.env.TZ` to a non-Vietnam value, same pattern as T-02-05.
  - Assert `formatViDateTime(fixedInstant)` (default options), `formatViDateTime(fixedInstant,
    { separator: "space" })`, and `formatViDateTime(fixedInstant, { withSeconds: true })`
    each produce the correct Asia/Ho_Chi_Minh wall-clock string, independent of the forced
    `TZ`.
  - Do not re-test `parseViDate` for timezone behaviour — it does no `Intl` work; leave any
    existing coverage for it as-is (this ticket only adds the missing timezone-focused
    cases for `formatViDateTime`).
- Final sweep (manual or scripted, not a new test file — record the result in this
  ticket's PR/commit description): run
  `grep -rn "new Intl.DateTimeFormat(" apps/backoffice-web/src apps/pos-web/src` and
  confirm every remaining match either (a) is inside `@erp/ui`'s own
  `date-time-format.ts` — not possible, since that package isn't under either app's `src`,
  so no match should originate there — or (b) already carries an explicit
  `timeZone: "Asia/Ho_Chi_Minh"` in its options literal. Any match that does neither means
  a call site from `00-intent.md` / AC-06 was missed and must be fixed before this ticket
  is done.
- Also grep for `.toLocaleDateString(` / `.toLocaleString(` under both apps' `src/` — the
  ledger-cash / deposit call sites migrated in T-02-03 used this form, not
  `Intl.DateTimeFormat` directly; confirm no other caller of that form was missed.
