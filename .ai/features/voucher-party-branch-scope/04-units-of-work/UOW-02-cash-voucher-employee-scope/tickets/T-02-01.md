# T-02-01 — Dựng fragment và bind parameter cùng chỗ

## Context

Refactor thuần, **không đổi hành vi**. Làm trước T-02-02 để nếu có gì vỡ thì biết ngay là
vỡ vì cách đánh số tham số, không phải vì phần lọc.

Hiện tại `lookup()` ghép thân UNION bằng `selectFragments(type)` nhưng mảng tham số lại
dựng tay ở chỗ khác:

```ts
const body = this.selectFragments(query.type).join('\n    UNION ALL\n');
const countRows = await this.dataSource.query(countSql, [actor.organizationId, searchPattern]);
const rows = await this.dataSource.query(pageSql, [actor.organizationId, searchPattern, pageSize, offset]);
```

Khi T-02-02 thêm `$3` vào riêng `EMPLOYEE_SELECT`, gọi với `type=customer` sẽ dựng câu SQL
không nhắc tới `$3` trong khi mảng vẫn có 3 phần tử → Postgres trả
`bind message supplies 3 parameters, but prepared statement requires 2`. Lỗi này chỉ hiện
ở đúng những loại đối tượng **không** liên quan tới thay đổi, nên rất dễ lọt review.

## Implementation notes

- Đổi `selectFragments(type: PartnerLookupType): string[]` thành
  `buildLookupQuery(type, orgId, searchPattern): { body: string; params: unknown[] }`.
  Mọi tham số sinh ra ở đúng chỗ fragment cần nó.
- `countSql` dùng `params` nguyên vẹn.
- `pageSql` nối `LIMIT $${params.length + 1} OFFSET $${params.length + 2}` — tính từ độ dài
  mảng, **không** viết cứng `$3`/`$4`.
- Ticket này chưa thêm tham số nào: sau refactor `params` vẫn là `[orgId, searchPattern]`
  cho mọi `type`. Đó là điều làm nó revert được độc lập.
- Không đụng `customerDebts` / `supplierDebts` / `customersWithDebt` / `suppliersWithDebt` —
  chúng có SQL riêng, không dùng `selectFragments`.
